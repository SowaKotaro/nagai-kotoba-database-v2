# A-01: 派生値の再計算（stats_helper・feature_range）

## 結論（3〜5 行）
- `stats_helper.rb` は SiteStatistics の集計結果を座標に写すだけで、派生カラム（`reading_length`・`mora_count`・`vowel_pattern` など）を自分では計算し直していない。ただし最頻値の判定だけは SiteStatistics と二重に持っている（A01-4）。また §7 が「拍位置」と呼んでいる値は、実際には「何番目の母音か」で、`MoraCount` の「拍」とは別物（A01-3）。
- `feature_range_controller.js` の `target_start` の数え方は、0 始まり・コードポイント単位（`Array.from`）。Ruby 側（`String#index`・`String#[start, len]`・`length`）と一致する。サロゲートペアは双方で 1 字、結合文字（濁点 U+3099 など）は双方で別の字として数える。手元で `ruby -e` と `node -e` を実行して確かめた（アプリ・テスト・DB は起動していない）。
- 問題は数え方ではない。「`surface[target_start, target.length] == target`」という前提を誰も検証していないこと（A01-1）と、`target_start` の自動補完が一意制約をすり抜ける経路があること（A01-2。推測）。
- コメントと実装の食い違いが既知の件のほかに 3 つあり（A01-5）、母音の数 5 も直書きされている（A01-6）。ビュー側の小さな再計算は C-17 / M-17 と同じ類型で、該当箇所を足すだけ（A01-7）。

## 指摘

### [A01-1] `target_start` が `target` の実際の出現位置を指すことを、どこでも検証していない
- 観点: E ／ 確度: 確認済み（コード上の経路。実機での再現はしていない）
- 根拠:
  - 検証は「含まれるか」だけ: `WordSenseFeature#target_within_surface`（app/models/word_sense_feature.rb:36-40）は `surface.include?(target)` しか見ない。`target_start` の検証は整数かつ 0 以上だけ（:18）。補完は `target_start.nil?` のときに限られる（:14, :31-33）。
  - 位置を前提にしている利用者は 2 か所:
    - 公開統計のハイライト: app/views/stats/_feature_ranking.html.erb:15-20 は `surface[start, length]` を切り出して強調する（データは site_statistics.rb:373 `feature_example`）。
    - コンソールでの復元: feature_range_controller.js:47-61 `restoreOne`。
  - 位置がずれる経路:
    - 表層形は同じフォームで訂正できる（`Admin::AnnotationQueue::WORD_ATTRIBUTES` の `:surface`。app/controllers/concerns/admin/annotation_queue.rb:13-14、入力欄は admin/annotations/show.html.erb:72-74 と annotation_decks/_card.html.erb:72-74）。
    - ところが feature-range が使う表層形は描画時の値で固定されている（`data-feature-range-surface-value`。_feature_fields.html.erb:6）。読みは `input` イベントを監視している（js:14-22）が、表層形は監視していない。
    - 保存済みの特徴は、表層形を変えても `target_start` が再計算されない（nil のときしか補完しないため）。
  - JS は位置が合わないと、黙って最初の出現に切り替える（js:52-61）。しかも `connect`（js:24-27）は `commit` を呼ばないので、隠しフィールドには古い `target_start` が残る。その結果、画面のハイライト（最初の出現）と保存される値（古い位置）が食い違う。
- 問題:
  - 公開の /stats §8 で、該当部分ではない文字列が強調されうる。`start` が表層形の長さを超えていても例外にはならず、空の強調が出るだけなので気づけない。
  - JS の docstring（js:38-40）は「保存済みの出現位置があればその箇所を」とだけ書いており、「合わなければ黙って先頭に替える」「隠しフィールドは直さない」ことが読み取れない。
- 提案:
  - 振る舞いを変えない範囲: `WordSenseFeature` と JS の `restoreOne` に、前提「`surface[target_start, target.length] == target`」をコメントで明記する。正の数え方（0 始まり・コードポイント）は schema.rb:131 のコメントと word_sense_feature.rb:4 にあるので、JS 側から参照する。
  - 計画書への提案（振る舞いが変わる）:
    - (a) モデルに「その位置に `target` がある」ことの検証を足す。
    - (b) 表層形を訂正したとき、`target_start` を最初の出現へ再補完する。
    - (c) feature-range が表層形の入力欄も監視する。
- リスク: 中 ／ 外部振る舞いへの影響: なし（コメントのみ）。(a)〜(c) を入れると、あり（保存が通らなくなる、またはハイライト位置が変わる）
- 先に必要な特性テスト:
  - モデル: 位置のずれた `target_start` を持つ特徴が、現状は有効になることを固定する。
  - 結合: §8 の実例が `target_start` どおりに切り出されることを固定する。stats_controller_test.rb:24 は先頭の一致しか見ていない。

### [A01-2] 同じ特徴・同じ `target` を 2 つ同時に作ると、どちらも先頭の出現に補完され、DB の一意索引で例外になる
- 観点: E ／ 確度: 推測（コードの経路は確認済み。提案 JSON に同じ特徴×`target` が 2 回入りうるかと、実際の例外は未確認）
- 根拠:
  - `ProposalApplication#build_features`（app/models/proposal_application.rb:82-95）は `target_start` を渡さない。重複判定の `existing`（:83）はループの前に一度だけ作るので、提案の中の重複は落ちない。`AnnotationProposal::SenseProposal#linguistic_features`（annotation_proposal.rb:50-54）も重複を除かない。
  - 同じ語義・特徴・`target` の行が 2 つ新規に作られると、`derive_target_start`（word_sense_feature.rb:31-33）が両方を最初の出現にする。モデルの uniqueness（:21）は DB しか見ないので、まだ保存されていない兄弟の行どうしは衝突を検出できない。その結果、`uq_wsf_sense_feature_target_start`（db/schema.rb:135）で `ActiveRecord::RecordNotUnique` になる。
  - この例外を受け止める場所が無い:
    - 一括承認: bulk_proposal_approvals_controller.rb:14 は `RecordInvalid` しか rescue しない。
    - 1 語コンソール: annotations_controller.rb:44 `@word.save` の周りに rescue が無い。
  - コンソールでも同じことが起きる。提案から組んだ行は `target_start` が空のまま描かれ、`connect` は `commit` しない（js:24-27）。そのため、該当部分をタップし直さずに保存すると空のまま送られる。
- 問題: `target_start` が作られた理由そのもの（「びしょびしょ…」のように同じ文字列が繰り返す語。word_sense_feature.rb:5-6）でこそ起きる経路になっている。
- 提案: 計画書への提案のみ。`build_features` の補完で、すでに組んだ兄弟の行が使った位置を飛ばし、次の出現を採るようにする。あるいは、提案の中の重複（特徴×`target`）を落とす。
- リスク: 中 ／ 外部振る舞いへの影響: あり（いまは 500 になりうるものが保存できるようになる）
- 先に必要な特性テスト: 同じ特徴×`target` を 2 回含む提案を `BulkProposalApproval#approve!` に通したときに、現状どうなるか（例外か保存か）を固定する。

### [A01-3] §7 の「拍位置」は「何番目の母音か」であって、`mora_count` の「拍」とは数え方が違う
- 観点: A・D ／ 確度: 確認済み
- 根拠:
  - `vowel_pattern` は母音だけを抜き出した列で、撥音・促音は消える。`VowelPattern::NON_VOWEL`（app/models/vowel_pattern.rb:8, :11-13）が、`RhythmPattern` の `n`（ん）と重ねた子音（っ）を落とす（rhythm_pattern.rb:8-9）。
  - 一方 `MoraCount` は撥音・促音を 1 拍として数える（mora_count.rb:8）。
  - 例: 「シンブン」は 4 拍だが、`vowel_pattern` は `iu` の 2 文字。§7 では「ブ」の `u` が「2 拍目」として描かれる。
  - それでも、どこもこの添字を「拍位置」と呼んでいる:
    - stats_helper.rb:147「層(拍位置)」、:150-153「15層」「10 拍ぶん」
    - site_statistics.rb:26-30, :266-267, :286-287
    - ja.yml:1253-1266「語頭からの拍位置」「%{position}拍目」
    - docs/stats.md:225
  - 同じページの §3 の切替（ja.yml:1214 `mora_hint`「長音『ー』も1拍」）は、本物のモーラ数を指している。
  - 検索の `WordSense.vowel_transition_at`（word_sense.rb:93-95, `SUBSTRING(vowel_pattern, …)`）も同じ添字を使う。そのため、図と検索結果のあいだでは食い違わない。
- 問題:
  - 同じページで「拍」が 2 つの定義で使われている。撥音・促音を含む語では、公開文言（「◯拍目まで届くのは…」）が実際の拍の位置とずれる。
  - コードを読む側も、`mora_count` と同じ数え方だと誤解しやすい。
- 提案:
  - 振る舞いを変えない範囲: stats_helper.rb:147 / site_statistics.rb:286 / docs/stats.md:225 に「位置は `vowel_pattern` の添字（n 番目の母音。撥音・促音は数えない。`mora_count` とは別）」と明記する。
  - 公開文言（ja.yml）を「◯番目の母音」などに改めるかは、計画書でオーナーに判断を仰ぐ。
- リスク: 低 ／ 外部振る舞いへの影響: なし（コメント・文書のみ）。文言を変えるなら、あり
- 先に必要な特性テスト: `SiteStatistics#build_vowel_transitions` に撥音を含む読み（例: シンブン）を入れ、層の数が `vowel_pattern.length` に従うことを固定する。

### [A01-4] 分布の最頻値を、ヘルパと SiteStatistics が別々に求めている
- 観点: B ／ 確度: 確認済み（実データで値が食い違うかは未確認）
- 根拠:
  - 波形バーの最頻: `stats_wave_bars` の `distribution.max_by { count }`（stats_helper.rb:28）が、「30+」にまとめた後のビンで判定する（まとめは site_statistics.rb:151-161）。
  - 数字の壁の最頻: `SiteStatistics#mode_from_counts`（site_statistics.rb:418-420、使うのは :94）が、まとめる前の件数で判定する。表示は _number_wall.html.erb:16。
  - 同数のときはどちらも小さい値を採る（`max_by` は最初の最大を返す。昇順のビン列なので小さい値になる。`ruby -e` で確認済み）。
- 問題: 「30+」の合計件数が単一の値の最大件数を超えると、§3 は「30+」を最頻（`--chart` のベタ。_length_chart.html.erb:21, :26, :35）として塗る。一方、数字の壁は別の値を最頻と示す。同じ「最頻値」を名乗る 2 つの画面要素で規則が違う。
- 提案: 最頻のビンは SiteStatistics の側で決め（`fill_distribution` が `mode: true` を立てるなど）、ヘルパはその印を写すだけにする。「まとめビンは最頻の対象にするか」の規則も 1 か所に書く。
- リスク: 低 ／ 外部振る舞いへの影響: なし（現状のデータで「30+」が最多でない限り）
- 先に必要な特性テスト: `stats_wave_bars` の単体テストが無い。stats_helper_test.rb はツリーマップと母音グラフしか扱っていない。最頻の判定（同数は小さい値・まとめビン）と `labeled`（両端と最頻）を先に固定する。

### [A01-5] stats_helper のコメントが実装・文書と食い違う（C-23 / SPEC-15 / SPEC-17 で既知のものを除く）
- 観点: A ／ 確度: 確認済み
- 根拠:
  - stats_helper.rb:150「15層で 818px」 ↔ 実装の幅は `xs.last + GRAPH_RIGHT`（:190, :243）= 14 + 80×14 + 14 = **1,148**。docs/stats.md:246 も「15層で 1,148px」。
  - stats_helper.rb:2-3「色・線種はビュー側の CSS クラスに任せる」 ↔ `graph_edges` は線の太さと濃さを計算している（:273-274）。ビューはそれを `stroke-width` / `stroke-opacity` 属性で出している（_vowel_graph.html.erb:47）。
  - stats_helper.rb:108「CSS の aspect-ratio と一致させる」（components.css:4276 も「必ず同じ比」） ↔ components.css:4365-4367 では、スマホのとき 3 / 5 にしている（docs/stats.md:220 には書いてある）。面積の比は保たれるが、squarify（:309-346）が正方形に近づける最適化は 3:2 を前提にしている、という事情がコード側からは読み取れない。
  - 既知: :356「2周期」は C-23 / SPEC-15、:25「docs/stats.md §1」は SPEC-17。
- 問題: 幅やキャンバスの比を変える将来の作業で、コメントを信じると誤った値を前提にしてしまう。
- 提案: :150 の数値を 1,148 に直す（あるいは数値を書かず式を示す）。:2-3 は「色は CSS、線の太さと濃さ（量の写像）はここで出す」に改める。:108 に「スマホは CSS 側で 3:5 に引き伸ばす（面積比は保たれる）」を添える。
- リスク: 低 ／ 外部振る舞いへの影響: なし
- 先に必要な特性テスト: 不要（コメントのみ）。幅は stats_helper_test.rb:92-97 が層の数との関係を固定している。

### [A01-7] ビューでの小さな再計算（C-17 / M-17 と同じ類型。該当箇所の追加だけ）
- 観点: D ／ 確度: 確認済み
- 根拠:
  - _vowel_graph.html.erb:92: 「最後の層まで届く割合」を `(last[:total] * 100.0 / total).round(1)` とビューで計算している。同じ規則は `SiteStatistics#percent`（site_statistics.rb:392-396）にある。
  - _entity_cell.html.erb:4 と _origins.html.erb:38: 塗りの濃さを `count / 先頭の件数` でビューが計算している。級数の段（`treemap_scale`、stats_helper.rb:283-288）は全体比で決めており、同じマスに 2 つの基準がある。
  - _feature_ranking.html.erb:15-20: 該当部分の切り出しをビューで行っている（A01-1 の利用者）。
- 提案: C-17 / M-17 の対応範囲に含める。ヘルパか SiteStatistics が `percent` / `fill` / 切り出し済みの 3 片を返すようにする。
- リスク: 低 ／ 外部振る舞いへの影響: なし
- 先に必要な特性テスト: stats_controller_test.rb に、§7 の注記の割合と §8 の強調部分の値を固定する。
