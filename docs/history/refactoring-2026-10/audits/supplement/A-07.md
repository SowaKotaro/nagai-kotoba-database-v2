# A-07: CSS に定義の無いクラス名（逆方向の照合）

## 方法（スクリプトの要点と、取りこぼしうるパターン）

スクリプトはリポジトリの外（セッションの scratchpad）に置いた。`a07_scan.rb`（本体）と `a07_models.rb`（補助）の 2 本。

- **定義側**: `app/assets/stylesheets/*.css` の全ルールについて、`{` の直前のセレクタ部から `.クラス名` を拾う。複合・子孫・`:not()` の中に現れるものも「定義あり」に数える。このため「別の組み合わせセレクタで定義がある」もの（分類 (b) の典型）は、機械的に除外済みになる。`[class*=…]` などの属性セレクタでクラスを指す書き方は 0 件だった（確認済み）。
- **使う側**:
  - ERB（`app/views/**/*.erb`）:
    - HTML の `class="…"` を拾う。中の `<%= … %>` は Prism で構文解析する。
    - `<% %>` の Ruby も Prism で解析し、次の値を集める: `class:`・`"class" =>`、`class_names`・`token_list`、`icon` の第 2 引数、`modifier:`、`content_for(:main_class, …)`、名前が `*_class`・`*_modifier(s)` のローカル変数への代入。
    - `data-*-class` 属性も拾う（該当 0 件）。
  - ヘルパ（`app/helpers/**/*.rb`）: ERB と同じ Prism 解析をかける。
  - i18n（`config/locales/*.yml`）: 値に埋め込まれた `class="…"` を拾う（`shiritori__char`・`cand-export__num` の 2 件。どちらも CSS あり）。
  - JS（`app/javascript/**/*.js`）:
    - `classList.add/remove/toggle/contains/replace`、`className =`、テンプレート内の `class="…"` を拾う。
    - `querySelector(All)`・`closest`・`matches` のセレクタ文字列も拾う。
    - Stimulus の `static classes` は 0 件だった（確認済み）。
  - 補助（a07_models.rb）: `app/models`・`app/controllers`・`lib` の文字列リテラルから BEM 風のトークン（`__` か `--` を含む）を拾う。該当は 0 件だった。
- **補間の展開**: `"block--#{値}"` の形は、値の出どころ（enum・定数・ヘルパの分岐）を読んで取り得る値を書き出し、1 つずつ CSS と照合した（下の「動的に組み立てるクラス」の表）。
- **フックの判定**:
  - JS・test からの参照は、クラス名の完全一致（前後が `[\w-]` でない）で `app/javascript` と `test/` を検索した。
  - CSS の履歴は `git log -E -G'\.<名前>([^a-zA-Z0-9_-]|$)' 1c07bbe -- app/assets/stylesheets` で調べた（前方一致の誤検出を避けるため `-S` ではなく境界付きの `-G` を使った）。
  - 検索式が機能することは、`.cand-status--held` で履歴が出ることで確かめた。
- **取りこぼしうるパターン**:
  - 照合はクラス名の単位で行っている。ある要素に付いたクラスに定義があっても、それが別の文脈（例: `.deck .is-on`）向けの定義だけのとき、その要素に実際に効く規則が無いことは検出できない。
  - CSS の無い要素でも、親の子孫セレクタ（例: `.bulk-review__table td`）で見た目が付いているものがある。この表では区別していない。
  - Ruby のメソッドの戻り値をそのまま `class:` に渡す箇所は「動的」として列挙して目視で展開した。メソッドの中で文字列を組み立てる形が将来増えると、拾えない。
  - `app/views/**/*.erb` 以外の HTML（`public/*.html` や `public/icon.svg` など）は対象外にした。

- 問題:
  - 同じ「CSS の無い BEM 名」が、根では DOM の目印、要素では書きかけ（または不要）と、意味の違うまま並んでいる。どれが意図的かをコードから判別できない。

- 提案:

    - ブロックの根は、CSS が無くても DOM の目印として付けてよい。
    - 要素・修飾子は、CSS かフック（JS・test）の用途があるときだけ付ける。
  - その規則に従い、要素 14 件のうち用途の無いものを削除する。`feature-rank__chip`・`vowel-graph-panel__pick` は A05-9 と重なる。
  - design.md:478 の `.radial-art` には「目印のみ。見た目は `.ring-art`」と添える。
- リスク: 低 ／ 外部振る舞いへの影響: なし（見た目は変わらない）

### [A07-4] 補間で組み立てる修飾子のうち 13 値は CSS が無く、「既定の見た目」なのか「書き忘れ」なのか区別できない（confidence は値域も閉じていない）
- 観点: D・E ／ 確度: 確認済み（意図は推測）
- 根拠（一覧の「動的に組み立てるクラス」の表）:
  - 候補の処理の `keep` に CSS が無い。`cand-bar__count--keep`・`cand-bar__action--keep`・`cand-choice__option--keep` の 3 つで、ほかの `expand`・`hold`・`reject` にはある。
  - `cand-status--` は、前処理中の 4 値（triage・expanding・notating・notated）に CSS が無い。
  - `tag-table__name--large`、`dup-note--none`（word_requests/_row.html.erb:12-13 のコメント「未収録は枠なしで静かに伝える」から、意図的と読める）、`ann-proposal__status--applied`（基本の `.ann-proposal__status` が success 色を持つので、既定がそのまま「反映済み」の見た目になっている）にも CSS が無い。
  - `ann-proposal__confidence--#{proposal.confidence}` は、外部の提案 JSON の値をそのままクラスにしている。`AnnotationProposal` には confidence の値域検証が無い（annotation_proposal.rb:100。`WordCandidate` には `CONFIDENCES = %w[high medium low]` と `inclusion` 検証がある: word_candidate.rb:23,63）。CSS があるのは `--low` だけ。
  - エスケープはされるので、XSS の問題ではない。
- 問題:
  - `--keep` を見たエージェントは、`--expand` と並ぶ規則がどこかにあると考えて探す。
  - 逆に、本当に色を付け忘れた値があっても、それと見分けがつかない。
  - confidence は、想定外の値（`"High"` など）が来ると黙って既定の見た目になり、i18n も `default:` で生の値を出す（_proposal.html.erb:15-16）。
- 提案:
  - 既定の見た目に任せる値は、各ブロックの CSS に「`--keep`・`--normal` などは既定の見た目なので規則を持たない」と 1 行コメントで列挙する（最小）。または、ビューでその値のときは修飾子を付けない。
  - confidence の値域は `WordCandidate::CONFIDENCES` と同じ定義を共有する。提案の取り込み時に検証するかどうかは、オーナーに確認する（取り込みの挙動が変わるので、計画書への提案のみ）。
- リスク: 低 ／ 外部振る舞いへの影響: なし（コメントのみの場合）。あり（confidence を検証する場合は、想定外の値を含む提案 JSON の取り込みが失敗するようになる）

### [A07-5] フック用クラスの命名が 3 流儀あり、`js-` 接頭辞が「JS が使う」ことを保証していない
- 観点: B ／ 確度: 確認済み
- 根拠:
  - **`js-` 接頭辞**（11 種）: 管理画面の注釈コンソール（_sense_fields・_feature_fields・_bulk_annotation）にしか無い。内訳は次のとおり。
    - JS が使う 7 種: `js-sense`・`js-reading`・`js-meaning`・`js-entity-none`・`js-genre-value`・`js-genre-current`・`js-variants`
    - test だけが使う 3 種: `js-genre-large/medium/small`
    - どこからも使われない 1 種: `js-feature`（J-19）
  - **見た目用の BEM 名を JS が流用**（9 種）:
    - CSS の無いもの: `cand-edit__cancel`（decision_list_controller.js:133）
    - CSS のあるもの: `.cand-word__edit`（decision_list:47）、`.bulk-review__reading-error`（reading_format:34）、`.row-check`（row_select:42,86,305）、`.cand-choice`（row_select:4 の `INTERACTIVE`）、`.ann-chip`・`.ann-chip__input`・`.ann-add`・`.ann-add__msg`（genre_picker・inline_add）
  - **Stimulus の target・data 属性**: ビューの `data-*-target=` が 110 箇所ある。ほかに `[data-row-group]`・`[data-nested-form-item]`・`input[data-sense-destroy]` など。
  - test 側も混在している。スタイルの無い BEM 名 9 種（一覧の (a) の「test だけ」から js- の 3 種を除いたもの）と、`js-genre-*` の 3 種を、同じように目印に使っている。
  - 規則を書いた文書は無い（`docs/`・CLAUDE.md を `js-` で検索して確認済み）。J-02 は「クラスでの約束」と「別ディレクトリの DOM に依存」を個別に挙げているが、命名規則には触れていない。
- 問題:
  - `js-` が付いていればスタイル無し・付いていなければ見た目用、という読み方が成り立たない。見た目用のクラスを改名・削除すると JS やテストが黙って壊れる（例: `.ann-chip` は CSS と JS の両方が使う）。
  - 逆に、`js-genre-*` は JS 用の名前なのに JS は読んでいない。
- 提案: J-02 で提案された「JS の地図」に、命名規則を 1 節足す（コードはすぐには変えない）。例:
  - 新規の JS フックは Stimulus の target か data 属性にする。
  - `js-` は既存の注釈コンソールだけに残す（増やさない）。
  - 見た目用クラスを JS・test が使う箇所は、CSS 側に「JS（〜_controller.js）も参照」と注記する。
  - `js-genre-*` の扱いは J-19 の提案（テスト用フックと明記）に従う。
- リスク: 低 ／ 外部振る舞いへの影響: なし（文書とコメントのみ）
