# SEO の月次の運用（手順・判定・施策の台帳）

月に 1 回、検索のデータと本番の実際を見て、次の一手を決めるための手順書。**誰が（どのモデルが）回しても同じ結果になる**ように、
数えるところはスクリプトに、判断するところは表にしてある。起動は `/seo`（スキル `seo-monthly-review`）。

| 文書 | 役目 |
|---|---|
| この文書 | **これからやること**の正。月次の手順（§3）、数字から次の一手を決める表（§4）、施策の台帳（§6） |
| [`seo-log.md`](seo-log.md) | **起きたこと**の記録。月ごとの数字、入れた施策の反映日と判定、月の所見 |
| [`seo-plan.md`](seo-plan.md) | 2026-11 の調査と計画、その経緯。サイトの事実（§4）、やらないこと（§7）、一次情報の出典（§11）、`.com` の移行（§12） |

基準値の正は `script/seo_monthly.py` の冒頭の定数で、この文書は名前で指す（値を写さない）。インデックスの規則の正はコード（seo-plan §4.2 に場所）。

## 0. 1 回の月次ですること

1. オーナーが Search Console のエクスポートを置く（§2。10 分ほど）。
2. スクリプト 2 本を回す（§3。集計と、本番の点検）。
3. 出た表を §4 に当てて、警報・検索の水準・施策の判定・次の一手を決める。
4. [`seo-log.md`](seo-log.md) に 1 か月分を足し、オーナーへ決まった形で報告する（§3 の 9）。

実施日は**毎月 12 日以降の最初に手が空く日**。Search Console の数字は 2〜3 日遅れて出るので、「過去 28 日間」の窓は実施日の 3 日ほど前で終わる。

## 1. 決まり

1. **数えるのはスクリプト、モデルは数えない。** 表示回数・順位・件数は `report.md` と `site-check.md` にある数だけを使う。CSV を自分で足し直さない。
2. **エクスポートに無い数字を書かない。** 検索回数の推定、競合の順位、被リンクの数などを作らない。分からないことは「分からない」と書く。
3. **確かめた事実と仮定を分けて書く。** 原因の説明は、確かめるまで仮定として書く。
4. **モデルがするのは提案まで。** 採否、本番の変更、Search Console の操作、Issue の優先度の変更はオーナーが決める。
5. **提案はテンプレート単位。** ページ 1 枚ずつの直しは出さない（同じ型のページが数千枚ある）。
6. **同じ切り口（単語詳細・ファセット面・ハブとホーム）に、判定待ちの施策を 2 つ重ねない。** どちらが効いたか分からなくなる。
7. **反映から 4 週間たつ前に判定しない。** 比べるのは、反映の 4 週間後から始まる 28 日間（seo-plan §8）。
8. **検索の水準が「戻った」になるまで、新しい施策を提案しない**（§4.2）。順位が揺れているあいだに入れても判定できない。
9. **公開済みの URL とクエリパラメータ名は変えない。インデックスの規則を触る案は、URL の空間が増えないことを先に確かめる**（CLAUDE.md §1。changelog の Issue 80・81）。
10. **seo-plan §7「やらないこと」と、[`design.md`](design.md) §12 の退けた案を、提案しない。**
11. 本番へ送るのは `script/seo_site_check.py` の GET（1 秒に 1 件ほど、約 40 件）と、公開語の写しの取得 1 回だけ。ほかに本番を叩かない。書き込みはしない。
    月次の外で随時回す Lighthouse（§10）は別で、ページを 1 枚ずつ開くぶんだけを送る。
12. 規則が変わったら、同じ PR でこの文書と seo-plan §4 とスクリプトの定数を直す（§9）。

## 3. 手順

番号の順に進める。途中で止める条件は各項に書いた。

1. **読む。** この文書の §1・§4、[`seo-log.md`](seo-log.md)（前の月の行、表 4 の判定待ち、前の月の所見）、seo-plan §4（サイトの事実）。ソースは読み直さない。
2. **入力を確かめる。** `ls research/inputs/seo/<月>/`。§2 の必須（1・2・5）が無ければ、足りないものを §2 の表の番号で伝えて**止まる**。無いまま進めて数字を補わない。
3. **集計する。** `python3 script/seo_monthly.py <月>`。`research/outputs/seo/<月>/report.md` ができる。
   本番につながらない環境では `--no-corpus`（表 C が省かれる）か、`--jp-file <保存済みの llms-full.txt>`。
4. **本番を点検する。** `python3 script/seo_site_check.py <月>`。`research/outputs/seo/<月>/site-check.md` ができる（1 分ほど）。月に 1 回だけ回す。
5. **警報を見る。** `report.md` の「0. 警報」に「警報」か「注意」があるか、`site-check.md` の「1. 問題」が「無し」でなければ、§7.1 へ進む。
   その月は新しい施策を提案しない（6 と 7 の記録は続ける）。
6. **判定する。** §4.2（検索の水準）→ §4.3（判定待ちの施策）→ §4.4（次の一手）の順に、表へ当てる。
7. **記録する。** [`seo-log.md`](seo-log.md) の表 1〜3 に、スクリプトが出した行（`report.md` の「6.」と `site-check.md` の「4.」）を**そのまま**足す。
   表 4 の判定を書き、「月ごとの所見」に 1 節足す（形は seo-log の冒頭）。
8. **収録の候補を渡す。** `report.md` の表 C のうち、個別の語（作品名・用語・固有名詞）で、読みが `WordSense::MIN_READING_LENGTH` 文字以上になりそうなものを、
   所見に「収録の候補」として並べる。登録予定単語に入れるのはオーナー（仕分けの画面に貼る。`research/README.md`）。打ち間違いや、語ではない検索語は並べない。
9. **報告する。** 次の形で、オーナーへ返す。項目の順と見出しを変えない。

   ```markdown
   ## SEO の月次（<YYYY-MM>）
   - 期間: <開始>〜<終了>（<日数> 日）
   - 警報: <無し / 内容>
   - 検索の水準: <戻った / 途中 / 戻っていない>（表示 1 日あたり <数>、前の月との差 <数>）
   - 登録済み: <数>（前の月との差 <数>）。sitemap.xml <登録/未登録>、sitemap-facets.xml <登録/未登録>
   - 公開語: <数>（前の月との差 <数>）。本番の点検の問題: <数>
   - 判定した施策: <施策> = <効いた / 変化なし / 悪化 / 判定不能>（根拠の数字）
   - 提案: <0〜3 件。§4.5 の形。無ければ「無し（理由）」>
   - オーナーの作業: <§6.3 のうち、今月やるとよいもの>
   - 収録の候補: <語の並び。無ければ「無し」>
   ```

10. **コミットは、オーナーの合図があってから。** 変わるのは `docs/seo-log.md` だけ（入力と出力は gitignore の下）。

## 4. 判定（数字 → 次の一手）

### 4.1 警報と注意

`report.md` の「0. 警報」に出る。条件の値は `script/seo_monthly.py` の定数。

| 種別と内容 | 定数 | すること |
|---|---|---|
| 警報: 登録済みが減った | `ALERT_INDEXED_DROP` | §7.1。新しい施策を止める |
| 警報: noindex による除外が増えた | `ALERT_NOINDEX_RISE` | §7.1。noindex の URL が湧いている疑い（Issue 80 と同じ形） |
| 警報: クロールの応答にサーバーエラー | `ALERT_SERVER_ERROR` | 本番のログと Puma の状態を見るようオーナーへ伝える（overview §11） |
| 注意: 登録を見送られたページが増えた | `WARN_NOT_INDEXED_RISE` | §2 の 6 のエクスポートを頼み、どの型のページかを見る。語が増えた分（公開語の差）で説明がつくなら、所見に書くだけ |
| 注意: クロールが 1 日だけ突出した | `WARN_CRAWL_SPIKE` | `site-check.md` の「閉じた URL」に問題が無いかを見る。無ければ所見に書くだけ。あれば §7.1 |
| 観測のみ: 切り口の表示が足りない | `MIN_IMPRESSIONS_TO_JUDGE` | その切り口の施策は、今月は判定しない（§4.3） |

### 4.2 検索の水準

`report.md` の §1 の先頭に出る。`.jp` 全体の、1 日あたりの表示回数で 3 つに分ける。

| 水準 | 条件（定数） | すること |
|---|---|---|
| 戻っていない | `LOW_IMPRESSIONS_PER_DAY` 未満 | 観測と点検だけ。施策を提案しない。**2027-02 の月次でもこの水準なら §7.2** |
| 途中 | あいだ | 観測と点検だけ。施策を提案しない。§6.3 のオーナーの作業と、話題の語の収録（§6.2 の S-6）は進めてよい |
| 戻った | `RECOVERED_IMPRESSIONS_PER_DAY` 以上 | はじめて「戻った」になった月の数字を、seo-log の表 1 で「基準」と記す（seo-plan §8 の基準の表の代わり）。§4.4 へ進む |

2026-11-13 に旧 `.com` の全 URL を `.jp` へ 301 にした。ドメインの移転では数週間は順位が揺れ、引き継ぎは保証されない（seo-plan §12.7）。
2026-12 の月次の窓は移行の直後なので、水準がどれでも観測だけにする。

### 4.3 判定待ちの施策

対象は、seo-log の表 4 で判定が「待ち」で、「判定できる最初の月」が今月以前のもの。**切り口ごとに**、上から順に当てる。

| 順 | 条件 | 判定 | すること |
|---|---|---|---|
| 1 | その切り口が「観測のみ」（§4.1） | 判定不能（表示不足） | 次の月へ持ち越す。3 回持ち越したら「判定せず終了」と書き、判定待ちから外す |
| 2 | 基準の月より、表示/日が 20% 以上増えたか、平均掲載順位が 1.0 以上よくなった | 効いた | 残す。所見に数字を書く |
| 3 | 基準の月より、表示/日が 20% 以上減ったか、平均掲載順位が 1.0 以上悪くなった | 悪化 | 差し戻しを提案する（§4.5 の形。差し戻すかはオーナー） |
| 4 | どちらでもない | 変化なし | 残す。判定待ちから外す |

- **基準の月**は、その施策の反映より前で、いちばん新しい月（seo-log の表 1）。数字は `report.md` §1.1 の「表示/日」と「平均掲載順位」。
- 単語詳細の切り口は、語が増えた分を効果と取り違えないよう、**表示/日 ÷ 公開語の数**（seo-log の表 3）でも比べ、両方が同じ向きのときだけ 2 か 3 にする。
- 同じ日に同じ切り口へ入った施策は、分けずに 1 行で判定する（2026-11-13〜15 の分。seo-log の表 4）。
- 2026-11 の行は期間が 3 か月で、最初の 1 週間に表示の 4 分の 3 が集まっている。2026-11-13〜15 の施策の基準には、
  08-17 以降の値（全体で 1 日 2.4 回。seo-plan §12.1）を使う。切り口ごとの内訳は取れていないので、2027-01 の判定は全体の水準（§4.2）で読み、
  切り口ごとの判定は「戻った」のあとの施策から行う。

### 4.4 次の一手の選び方

水準が「戻った」で、警報が無いときだけ。**1 回の月次で提案する新しい施策は 1 つ**（切り口が違えば 2 つまで）。

1. §6.2 の候補を、S-1 から番号順に見る。
2. 「着手の条件」をすべて満たし、その切り口に判定待ちが無い（§1 の 6）ものを選ぶ。
3. 満たす候補が無ければ、「提案: 無し（条件を満たす候補が無い）」と報告する。無理に作らない。
4. 台帳に無い案を思いついたら、施策として提案せず、「台帳に足す候補」として §6.2 と同じ項目で書いて出す（足すかはオーナー）。

### 4.5 提案の書き方

```markdown
- 施策: <§6.2 の番号と名前>
- 切り口: <単語詳細 / ファセット面 / ハブとホーム>
- 根拠: <report.md の節番号と数字。確かめた事実>
- 仮定: <効くと考える理由。確かめていないこと>
- 変える場所: <ファイルとシンボル>
- 変えないもの: <URL・h1・インデックスの規則など>
- 判定できる最初の月: <反映の 4 週間後から 28 日間が入る月>
```

## 5. 本番の点検で見ているもの

`script/seo_site_check.py` が見る。期待する値はスクリプトの冒頭の定数（`HUBS`・`MUST_NOINDEX`・`MUST_404`・`MUST_REDIRECT`）。

| 見るもの | 問題にする条件 |
|---|---|
| robots.txt | 200 でない。`Sitemap:` に 2 つのサイトマップが無い。公開ページを Disallow している |
| `sitemap.xml`・`sitemap-facets.xml` | 200 でない、空、canonical のホストでない URL、単一の条件でない面 |
| インデックスさせるページ（`HUBS` の 10 枚、単語詳細を等間隔に 5 枚、ファセット面を種類ごとに 1 面） | 200 でない、noindex、title が空、meta description が無い、canonical が自身でない、h1 が 1 個でない、JSON-LD が読めない、title か説明文がほかと同じ |
| ファセット面の突き合わせ | サイトマップに載っているのに、ハブからリンクされていない面 |
| インデックスさせない URL（`MUST_NOINDEX`） | noindex が付いていない（2 ページ目、範囲外のページ、並び替え、シャッフル、0 件の面、条件 2 つ、検索フォーム） |
| 存在しない URL（`MUST_404`） | 404 でない（実在しないマスタ id。Issue 81） |
| リダイレクト（`MUST_REDIRECT`） | 301 でない、行き先が違う（旧 `.com`、www、http） |

あわせて、seo-plan §4.3 の表を取り直す数（公開語、ハブからリンクされた面、サイトマップに載る面、条件ごとの内訳）を出す。
「載らない面」は、公開語義が `IndexableFacets::SITEMAP_MIN_COUNT` に届かない薄い面の数になる。

問題が出たら §7.1。規則のほうを変えたために出た問題なら、スクリプトの定数を直す（§9）。

## 6. 施策の台帳

### 6.1 入れたもの

反映日と判定の正は [`seo-log.md`](seo-log.md) の表 4。中身の記録は seo-plan §5 の「実装の記録」と §12.6。

### 6.2 これから入れる候補

番号順に見る（§4.4）。どれも、着手の前にオーナーの採否が要る。

**S-1. 単語詳細の title に「読み方」「意味」を足す**（seo-plan §5 B-3・判断点 4）

- 切り口: 単語詳細。
- 着手の条件: `report.md` §1.7 の末尾が「満たす」（`INTENT_SHARE_TO_PROPOSE`）。単語詳細の切り口が「観測のみ」でない。
- 変える場所: `app/views/words/show.html.erb` の `content_for :title`。文言は `config/locales/ja.yml` に新しいキー（`words.show.meta_title`）で置く。
  表層形が長い語は足した分が検索結果で切れるので、足す上限の字数を `WordsHelper` に定数 1 つで持ち、超える語はいまのまま（表層形だけ）にする。
- 変えないもの: URL、h1、meta description、構造化データ、共有カード。レイアウト（`app/views/layouts/application.html.erb`）は `<title>` と og:title に
  同じ `page_title` を使っているので、og:title は表層形のまま残るように分ける。
- テスト: `test/integration/meta_tags_test.rb` の title の行に、足す場合と、上限を超えて足さない場合を並べる。
- 影響: 公開している全部の単語詳細の title が一度に変わる。影響範囲を説明してから行う。

**S-2. 語義が少ない薄い面を noindex,follow にする**（seo-plan §5 C-3 の選択肢 2・判断点 2）

- 切り口: ファセット面。

## 7. うまくいっていないとき

### 7.1 警報・注意・点検の問題が出た

1. 新しい施策の提案を止める（記録は続ける）。
2. `site-check.md` の「1. 問題」を読む。「閉じた URL」「リダイレクト」に問題があれば、それが原因の第一候補。
3. noindex による除外や、登録を見送られたページが増えたときは、§2 の 6 のエクスポート（URL の一覧）を頼み、集計をやり直す。
   `report.md` の「理由ごとの URL の一覧」で、どの切り口・どのクエリパラメータが増えたかを見る。
4. 新しい型の URL が湧いていたら、その URL へのリンクを出しているビューを探す（`grep` でパラメータ名を引く）。
   [`history/changelog.md`](history/changelog.md) の Issue 80・81 が同じ型の事故の記録。
5. **robots.txt で塞がない。** 塞ぐと Google が noindex と canonical の訂正を読めなくなる（理由は `app/views/robots/show.text.erb` のコメント）。
   直すのは、生成元を絶つことと、noindex・canonical・404 を正しく返すこと。
6. 原因と直し方をオーナーへ報告し、直すなら Issue を起こして PR にする（インデックスの規則の変更なので、影響範囲を先に説明する）。

### 7.2 2027-02 の月次でも、検索の水準が「戻っていない」

`.com` を寄せた効果が出ていないことになる。施策を足す前に、次の順で確かめて、結果をオーナーへ報告する。

1. `site-check.md` のリダイレクトに問題が無いか（旧 `.com` の 301 が生きているか）。
2. §2 の 7（`.com` の検索パフォーマンス）で、`.com` の表示が減っているか。減っていなければ、Google が 301 をまだ処理していない。
3. `notes.md` の URL 検査（ホームと単語詳細）の状態。
4. seo-plan §12.3 の切り分けの表を、同じ確かめ方でやり直す。
5. ここまでで技術的な原因が無ければ、「アドレス変更」を前倒しするか（§6.3）、単語詳細の中身（S-5）を先にするかを、オーナーに判断してもらう。

## 10. Lighthouse（随時。月次の手順には入れない）

`python3 script/seo_lighthouse.py <月>`。本番の代表的なページ（スクリプトの `PAGES` と、一覧の先頭の単語詳細 1 枚）を、Google 公式の診断
[Lighthouse](https://github.com/GoogleChrome/lighthouse) で 1 枚ずつ測り、`research/outputs/seo/<月>/lighthouse.md` に点数と満点でない項目を出す。
ページを指定するときは、月のあとにパスを並べる。

- **何を見るか**: ブラウザで開いたときの性能・アクセシビリティ・ベストプラクティス・SEO の基礎。§5 の点検（検索エンジンから見える規則）とは重ならない。
- **いつ回すか**: レイアウト・CSS・JS を大きく変えて本番に出たあと。月次のたびには回さない（§3 に入れない）。
- **読み方**: スマホの条件で 1 回測った値なので、性能の点は回ごとに数点ぶれる。1 回の上下で判断せず、満点でない項目の顔ぶれが変わったかを見る。
  性能の原因の調べ方と過去の対処は [`history/performance-report.md`](history/performance-report.md)。
- **依存**: Lighthouse は `npx` で都度取り寄せる（プロジェクトの依存に足さない）。Node と Chrome が要る。Chrome は `CHROME_PATH`、
  無ければシステムテスト用に入っているものを使う。
- **CI には組まない**: main への merge がそのまま本番デプロイになり、CI を待たないので、関門にならない（Lighthouse CI を見送った理由）。
- 最初に測った日は 2026-11-15（4 枚とも SEO は満点。数字は seo-log の所見）。
