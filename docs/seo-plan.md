### 2.2 共通する、使える教訓

1. **検索のデータは道具から渡す。** モデルは検索回数・掲載順位・被リンクを知らない。渡さずに聞くと、それらしい数字を作る。
2. **数字を作らせない。** 確かめた事実と仮定を分けて書かせる。
3. **公開と本番の変更は人が決める。** モデルに任せるのは調査・監査・下書きまで。
4. **ページ単位ではなくテンプレート単位で直す。** 同じ型のページが 2,569 枚あるサイトでは、1 枚ずつ直す意味が無い。
5. **サイトの事実を 1 か所にまとめて渡す。** 毎回ソースを読み直させない。
6. **定例にする。** 1 回の大掃除ではなく、週次で「もう少しで 1 ページ目」の検索語を見る。
7. **発見とインデックスが先。** 見つけてもらえていないページの文言を磨いても意味が無い。

## 4. 現状の棚卸し（2026-11-11 実測）

### C. 発見とインデックス

**C-1. ファセット面の登録状況を確かめる（コード不要。A-1 と同時）。**

**C-2. ファセット面のサイトマップを別ファイルで出す（中。判断点 3）。** → **2026-11-13 に実装した**（`/sitemap-facets.xml`。下の「実装の記録」）。
798 面を載せた 2 つ目のサイトマップ（たとえば `/sitemap-facets.xml`）を足し、robots.txt に `Sitemap:` の行を 1 つ足して、Search Console に送る。

- ねらいは 2 つ。Google に「登録してほしい面」を伝えることと、**Search Console でファセット面だけの登録状況を追えるようにすること**
  （サイトマップごとに集計が出る。いまは単語詳細と混ざって見えない）。既存の `sitemap.xml` に足す案もあるが、分けて見られなくなる。
- **URL の空間は有限**（マスタの行数と、実在する文字数・モーラ数の値だけ。§4.3 の 798）。条件の組み合わせ・並び替え・ページ送りは載せない。
- 「どの面をインデックスさせるか」の規則が、ビュー（`indexable`）とサイトマップの 2 か所に分かれないようにする。
  規則をモデル（`WordSenseSearch` か、面を列挙する集計クラス）へ移し、両方がそれを使う。件数は `PublishedSenseCounts` がすでに持っている。
- lastmod は付けない（面の更新日時を正確に出せないため。Google は不正確な lastmod を無視する）。
- 新しい公開 URL が 1 つ増える（一度出すと変えられない）。重い応答なので、既存の sitemap と同じく条件付き GET とキャッシュを付ける（`SitemapsController` の作り）。

**C-3. 語義が 1〜2 件の薄い面の扱いを決める（判断点 2）。**
798 面の 3 分の 1 が、語義が 1〜2 件だけの一覧になっている（§4.3）。その語の単語詳細がすでにあるので、検索エンジンから見れば中身の薄いページになる。選択肢は 3 つ。

1. **現状維持**（1 件以上ならインデックス可）。収録が進めば埋まる。
2. **しきい値未満は noindex,follow にする。** `indexable` の「1 件以上」を「N 件以上」に上げる。しきい値は `WordSenseSearch` に定数として 1 つだけ置く。
   語が増えれば自動でインデックス可に変わる。
3. **インデックスの規則は変えず、サイトマップ（C-2）にだけ、しきい値以上の面を載せる。**

推奨は、**C-1 の結果を見てから**。薄い面が「クロール済み - インデックス未登録」に並んでいるだけなら害は小さいので 3、
薄い面のせいで厚い面のクロールが遅れている様子があれば 2。B-2 を入れた特徴の面は、語が少なくても解説があるので、しきい値から外せる。

**C-2・C-3 の実装の記録（2026-11-13）。** C-1 の内訳（ファセット面の登録数）が取れないまま、推奨どおりに入れた。内訳はこのサイトマップを Search Console に送れば出るので、C-1 の代わりにもなる。

- C-3 は選択肢 3 にした。**インデックスの規則は変えていない**（1 件以上なら index のまま）。サイトマップに載せるのは、公開語義が
  `IndexableFacets::SITEMAP_MIN_COUNT` 件以上の面だけ。しきい値は、この節が「薄い」と呼んだ 1〜2 件を外す値にした。
  選択肢 2（しきい値未満を noindex）へ進むかは、サイトマップごとの登録数を見てから決める。
- 面の列挙は `IndexableFacets` に 1 か所。種類は `WordSenseSearch::INDEXABLE_FACET_KEYS`、件数は `PublishedSenseCounts`（索引のページと同じ集計）、
  文字の面は索引の 50音表の字だけ。条件の組み合わせ・並び替え・ページ送りは載せない。
- 載せた URL が、開くとインデックス可で canonical が自身を指すことは、結合テスト（`SitemapsControllerTest`）が載せた URL の全部について確かめる。
- 開発 DB（公開 1,499 語）で数えると、面は 654、そのうち載るのは 400。面の一覧は、ハブとホームのリンクから集めた単一条件の URL と過不足なく一致した
  （`IndexableFacets.all` と、`/genres`・`/entity_types`・`/linguistic_features`・`/browse`・ホームの `a[href^="/words?"]` の突き合わせ）。

### E. 鮮度（話題の語を、その日のうちに）

Day-One Page の考え方（§2.1）を、このサイトの形に直す。新しいページの型は作らず、**毎朝の `/harvest`（ニュースからの収穫）で見つかった話題の長い言葉を、
その日のうちに収録する**。話題になった直後は検索が集中し、まだどの辞書にも載っていないので、単語詳細がそのまま答えになる、という見込み（仮説。下の 3 つ目で確かめる）。

- 対象は、収穫のなかでも「いま検索されていそうな語」（新しい作品名・商品名・流行語）だけ。全部を急がない。
- 収録したら、Search Console の URL 検査からインデックス登録をリクエストする（1 日に数件までの手作業。話題の語だけ）。
- 1 週間後に、その語の表示回数を A-4 の観測で見る。効いていなければやめる。
- 収録の基準は変えない（[`annotation-guidelines.md`](annotation-guidelines.md)）。急いで質を落とすと、このサイトの売り（運営者が精査している）を損なう。

### F. 外からの言及

言及やリンクを集めるための働きかけはしない（Google の文書が不要と書き、スパムポリシーにも近い。Wikipedia などへの自薦もしない）。
代わりに、**引用する理由のあるもの**を置く。D-1 の統計、D-2 のデータセット、JSON API（Issue 110）、「今日の一語」の投稿（Issue 47）。

### 12.6 `.com` を寄せる場合の形（判断点 9 の材料）

リダイレクト無しで `.com` を止めると、評価がすべて消える。寄せるなら 301 で、行き先は 3 種類になる。

| `.com` のページ | 件数（2026-11-12） | 301 の行き先 |
|---|---|---|
| ホーム・一覧などのハブ | — | `.jp` の対応するページ |
| `.jp` に公開済みの語 | 990 | 対応する `.jp` の `/words/:id`（§12.5 の対応表） |
| 排除した語・未移行の語 | 5,258 | `.jp` の `/words`。評価は引き継がれない。未移行の語は、公開されたら対応する語へ付け替える |

- **得るもの**: サイト名での検索と、`.com` の持つ評価・被リンク・1 日約 30 セッションが `.jp` に向かう。§12.3 で残った「サイト全体の評価の低さ」に効く見込みがある手は、いまのところこれだけ。
- **失うもの**: 流入は多くて 90 日で 165 セッション（§12.4）。ただし `.jp` に無い 5,258 語は、移行が進むまで検索から消える。
  ホームに着く利用者は、6,248 語ではなく 2,569 語のサイトを見ることになる（確定事項 22 の理由だった点）。
- **段階的に寄せる案**（収録済みの語とハブだけを 301 し、残りは `.com` で動かし続ける）は、差が上の 165 セッションの範囲に収まるうえ、対応表を足し続ける手間がかかるので勧めない。
- **進め方**: 対応表を移行のたびに作り直して nginx の対応を差し替える。全部終わったらドメイン単位の 301 に切り替え、Search Console の「アドレス変更」で知らせる
  （`.com` は 2026-11-12 にドメイン プロパティとして登録済み）。インフラの変更なので、Issue 27 として影響範囲を説明してから行う。
- **決める前に見るもの**: `.com` の Search Console の検索パフォーマンス（サイト名での検索がどれだけあるか、どの語で出ているか）。→ §12.7。

**対応表の作り直し（移行が進むたびに）。** `.jp` で語が公開されると、`/words` へ飛ばしていた語に行き先ができる。

1. `python3 script/com_redirect_map.py` を打つ。本番の `/llms-full.txt` を 1 回読み、`research/outputs/com-redirect/com-to-jp-words.map` を作り直す。
   入力の `research/inputs/com-words.csv`（旧 `.com` の全語の id・表層形・読み）は gitignore の下にあり、作り直さない。
   **`research/inputs/seeds.txt` は移行した分が先頭から消えていく作業用のファイルなので、ここから作り直せない**（失ったら旧 `.com` の DB から書き出す）。
2. 出力の末尾に並ぶ「読みだけ一致」を目で確かめる（表記の違う同じ語かどうか）。
3. `.com` のサーバの対応表（`/etc/nginx/com-to-jp-words.map`）を差し替え、`sudo nginx -t` で検査してから `sudo systemctl reload nginx` する。

**サーバ側の置き場所**（`.com` と `.jp` は同じサーバ。リポジトリの外にあり、Capistrano は触らない）。

| ファイル | 役割 |
|---|---|
| `/etc/nginx/com-to-jp-words.map` | 対応表の本体。差し替えるのはこれだけ |
| `/etc/nginx/conf.d/com-to-jp.conf` | 対応表を読む `map` の定義 |
| `/etc/nginx/sites-available/nagai-kotoba-database.com` | `.com` の全 URL を 301 にする設定。元の設定（アプリへの `proxy_pass`）は同じ場所の `.bak-20261113` |

**2026-11-13 に反映した。** 反映後に外から確かめた行き先は、`/`→`/`、`/words`（クエリつきも）→`/words`、`/words/47`→`/words/46`、`.jp` に無い語→`/words`、
`/stats`・`/about`→同じパス、`/request`→`/requests/new`、`/login`→`/`。www と http からも同じ先に着く。

旧アプリ（Upper10）は `127.0.0.1:8000` で動かしたままにしてあり、設定を戻して reload すれば元に戻る。止めるのは、検索が落ち着いてから（オーナーの見込みは年明けごろ）。
