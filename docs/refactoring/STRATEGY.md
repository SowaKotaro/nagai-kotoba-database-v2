# 大規模リファクタリングの進め方（方針）

> この文書は**進め方の決まり**だけを書く。変わるのは方針を見直したときだけ。
> - **いまどこまで進んだか**は [`LEDGER.md`](LEDGER.md)（台帳）だけが持つ。
> - **何をなぜ直すか**は計画書 [`ai-legibility-plan.md`](ai-legibility-plan.md) だけが持つ。
> - 再開するときは `/refactor-resume` を打つ（`.claude/commands/refactor-resume.md`）。
>
> 2026-10-02 にオーナーと決めた。

## 1. 前回の失敗と原因

前回（2026-09 下旬）は、Opus 5.5・effort max・サブエージェント 8 体の並列で監査した。
その結果、次のことが起きた。

- 利用上限（5 時間枠）に途中で当たった。
- 再開したときには会話の文脈が消えていて、同じ箇所を調べ直した。
- メモリの記述と、ファイルに書き出した成果物が別々に育ち、食い違った。

**原因は、進捗の正本が会話の文脈とメモリにあり、ファイルと git に無かったこと。**

また、effort max と並列の組み合わせは、上限に当たる時刻を早めただけだった。上限はトークン量で決まる。
8 体を並列にしても総消費量は変わらず、短くなるのは待ち時間だけで、中断したときは 8 本が同時に途中で止まる。

## 2. 原則：中断を前提に設計する

「1 つの枠で終わらせる」ことは目指さない。**どこで切れても、失うのは作業 1 単位まで**にする。

### 2.1 状態はリポジトリだけに置く

| 何を | どこに | 書いてよい者 |
|---|---|---|
| 進め方の決まり | `STRATEGY.md`（この文書） | オーナーの合意があるときだけ |
| 何をなぜ直すか（項目の中身） | 計画書 `ai-legibility-plan.md` | リーダー（段階 3 でだけ改訂する） |
| 進捗・項目の状態・作業ログ | 台帳 `LEDGER.md` | **リーダーだけ** |
| 監査の生の記録 | `audits/*.md` | 担当のサブエージェント（自分のファイルだけ） |

- **auto-memory に進捗を書かない。** メモリが持つのは「台帳は LEDGER.md、再開は /refactor-resume」という案内だけにする。
- **項目の状態は計画書に書かず、項目の中身は台帳に書かない。** 同じ情報を 2 か所に置くと必ずずれる。
- 会話の中で分かったことも、台帳かファイルに書いてコミットするまでは「存在しない」ものとして扱う。

### 2.2 段階を分け、段階の間に承認を挟む

段階は **監査 → 計画（承認）→ 実行** の順に進め、混ぜない。段階の定義は台帳の §2 に置く。

- 実行中に見つけた計画外の問題は、その場では直さない。台帳の「受付箱」（§5）に書いて先へ進む。
- 計画を書き直すのは段階の切れ目だけにする。

### 2.3 作業は小さな単位に切り、終わるたびにコミットする

- **1 単位は、5 時間枠の 1/3 以下で終わる大きさ**にする。目安として、監査なら 3〜5k 行、実行なら計画の 1 項目。
- 1 単位が終わったら、成果物と台帳の更新を**同じコミットで**入れる。コミットされていない成果は、無かったものとみなす。
- 実行の各コミットでは、合格判定（計画書 §0.3）をすべて通す。
  `docs/refactoring/` だけを変えるコミットは、合格判定を省いてよい。

### 2.4 指摘はコミットに固定する

- 指摘には「ID ＋ `path:line` ＋ シンボル名 ＋ 調べたときのコミットハッシュ」を付ける。
- 再開したときや時間が空いたときは、
  `git diff <調べたときのハッシュ>..HEAD --stat -- <対象>` で**変わったファイルだけ**を確かめ直す。
  変わっていないファイルは調べ直さない。
- 既存の監査記録（`audits/`）の行番号は `a04f375` 時点のもの。

### 2.5 再開の手順は固定する

毎回の最初に `/refactor-resume` を打つ。手順はコマンドの中に書いてあり、その場の判断で変えない。

## 3. effort の使い分け

effort は高いほど 1 問を深く考えるが、5 時間枠で終わる単位が減って、中断が増える。
監査の精度を決めるのは、主に網羅性と一貫性であり、それは effort ではなく単位の切り方と記録の仕方で決まる。
そのため、**普段は high にして、判断の要所だけ max にする**。

| 作業 | effort |
|---|---|
| 既存の監査の棚卸し・指摘の仕分け | high |
| ファイル単位の補完監査 | high |
| **計画の確定（正典パターンの決定・順序付け）** | **max** |
| **承認前の計画レビュー（反証役）** | **max** |
| 機械的な置き換え・リネーム・文書の修正 | high |
| **振る舞いが変わりうる箇所の改修**（コールバック・派生値・照合順序・キャッシュ） | **max** |

- 各項目の推奨 effort は台帳に書く。`/refactor-resume` は、いまの effort が推奨より低ければ止まる。
- 精度は effort ではなく、**検証**で担保する。
  - 実行: 1 項目ごとに合格判定を通す。
  - 監査: 指摘は、別のエージェントに反証させてから計画に採用する。

## 4. エージェントの使い方

- モデルは Opus 5.5 のまま使う。
- サブエージェントは**同時に 2〜3 体まで**にする。迷ったら直列にする。
- サブエージェントには、書き込んでよいファイルを 1 つだけ渡す。台帳と計画書はリーダーだけが触る。
- サブエージェントが途中で止まったら、その単位は台帳上で「未着手」に戻して、やり直す。

## 5. ブランチと公開

- 作業ブランチは常に **`feature/refactoring` の 1 本だけ**にする。並行してブランチを作らない（台帳が分岐するため）。
- **main への push や merge は、そのまま本番デプロイになる**（`.github/workflows/deploy.yml` は main への push で動き、
  CI の完了を待たない）。push・PR・merge は、オーナーの指示があるときだけ行う。
- merge の区切りは、実行の「群」（計画書 §6）の切れ目にする。
  merge した後は、最新の main から `feature/refactoring` を切り直して続ける。

## 6. やらないこと

- 調べ直すとき、変わっていないファイルを読み直さない（§2.4）。
- 台帳を通さずに、メモリや会話の記憶を根拠にして「終わっている」と判断しない。
- 計画書に無い変更を、実行の段階で混ぜない。見つけたものは受付箱に入れる。
