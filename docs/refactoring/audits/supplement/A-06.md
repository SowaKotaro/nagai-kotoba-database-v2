# A-06: マスタを新設する経路の正規化と検証

## 結論（3〜5 行）

- 本番で走るマスタ新設の経路は **4 系統**ある。管理画面の 3 系統（その場追加・タグ統括管理・提案の新設候補）と、デプロイ時の `SeedCatalog.seed_all!` である。ほかに開発専用の経路が 2 つある。どのマスタのモデルにも名前の正規化（`normalizes` / `before_validation`）は無い。
- 正規化は**その場追加だけ**で行っている。前後の空白（全角を含む）を落とす。提案の新設候補とタグ統括管理は名前をそのまま保存する。`utf8mb4_0900_*` は NO PAD なので、末尾に空白が付いた名前は既存のマスタとは別物として作られる。NFKC や全角半角の正規化はどの経路にも無く、照合順序 ai_ci が比較のときに吸収している。
- 「名前が既にある」ときの扱いも経路ごとに違う。その場追加は理由を返す。新設候補は黙って既存のマスタを返す。タグ統括管理は汎用の「taken」を返す。**C-20 の主張は正しいので「確認済み」に上げる**。ただし「経路が 3 つ」は seed の経路を数えていない。また、作れる種別は経路ごとにほぼ重ならない。
- `RecordNotUnique` が 500 になる**決定的な経路は無い**。モデルの一意性検証と DB の一意索引は、同じ列の同じ照合順序で判定している。500 になりうるのは競合したときだけで、`Admin::TagsController#create` / `#update` がそれに当たる。

## 指摘

### [A06-1] 名前の正規化はその場追加にしか無く、新設候補とタグ統括管理では前後に空白の付いた別マスタができうる
- 観点: B・E ／ 確度: 確認済み（コードの差は読んで確かめた。NO PAD による「別物扱い」は MySQL の照合順序の仕様から導いたもので、実行はしていない）
- 根拠:
  - 前後の空白を落としているのは `InlineMasterCreatable#inline_master_name`（inline_master_creatable.rb:41-43）だけ。
  - `ProposedMasterCreation#create_named`（proposed_master_creation.rb:31-35）と `#create_genre_small`（:43-46）は、`SenseProposal#entity_type_name` / `#part_of_speech_name` / `#genre_path`（annotation_proposal.rb:36-39）の値をそのまま渡している。取り込み（annotation_proposal_import.rb:52）も `slice` するだけ。
  - `Admin::TagsController#create` / `#update`（tags_controller.rb:22,38）は `tag_params`（:87-89）をそのまま使う。
  - モデル（上の表の「モデル側」）には `normalizes` も `before_validation` も無い。CLAUDE.md の「派生値は自動生成」の方針はマスタ名には及んでいない。
- 問題: payload に `"英語 "` のような末尾空白があると、`resolved_*` の `find_by` は NO PAD のため既存の「英語」に当たらず、新設候補として表示される。ボタンを押すと「英語 」という別のマスタが作られ、一意性検証も通ってしまう。見た目は同じ名前のマスタが 2 つ並び、統計・絞り込みが割れる。同じ入力でも、その場追加なら起きないので、経路によって結果が違う。
- 提案: 前後の空白の除去を 5 つのモデル（`TagMaster` を include するもの ＋ `Genre`）の `normalizes :name` に移し、コントローラ側の `inline_master_name` の除去はやめる。`normalizes` は `find_by(name:)` / `where(name:)` にも効くので、提案の名前解決（`resolved_*`）も同じ規則に揃う。
- リスク: 中 ／ 外部振る舞いへの影響: あり（管理画面だけ。末尾に空白のある提案名が既存のマスタに解決されるようになり、新設候補のボタンが出なくなる。公開面は変わらない）
- 先に必要な特性テスト:
  - `ProposedMasterCreation` に前後空白付きの名前（`"英語 "`、全角空白）を渡すと、いまは別レコードが作られることを固定する（test/models/proposed_master_creation_test.rb に追加）。
  - `TagsController#create` に前後空白付きの名前を送ったときの保存値を固定する（tags_controller_test.rb:109 の隣）。
  - その場追加の側はすでに genres_controller_test.rb:51 にある。

### [A06-2] 既存の名前と衝突したときの扱いが 3 経路で違い、新設候補は表記の違う既存のマスタを黙って返す
- 観点: B ／ 確度: 確認済み
- 根拠:
  - P1: 同じ表記なら既存を返し、ai_ci で衝突する別表記なら 422 で理由を返す（inline_master_creatable.rb:21-26、ja.yml:956）。
  - P2: どちらの場合も検証の `taken` を返すだけ（tags_controller.rb:23-27）。
  - P3: `find_or_create_by!` の `find_by` が ai_ci なので、別表記の既存をそのまま返す（proposed_master_creation.rb:34,46）。デッキでは「「%{name}」を追加して、このカードに入れました」（ja.yml:1084）と、作っていないのに「追加」と出る（annotation_decks_controller.rb:77）。
- 問題: 同じ「マスタを 1 件足す」操作が、画面によって「理由つきで止める」「汎用エラー」「黙って既存を使う」に分かれる。どの扱いが正なのかがコードからは読めない。いまは P3 のボタンが出るのは `resolved_*` が nil のときだけなので、ほとんど表に出ない。ただし語種では表に出る（A06-4）。
- 提案: 衝突の方針（同じ表記なら既存を返す、別表記なら止めて理由を出す）を 1 か所に置く。たとえば `TagMaster` / `Genre` に共通のクラスメソッド、または小さなサービスにして、P1 と P3 から呼ぶ。P2 も同じ文言で失敗させる。C-20 の提案と同じ改修項目に束ねる。
- リスク: 低〜中 ／ 外部振る舞いへの影響: あり（管理画面の新設候補とタグ追加で、衝突時のメッセージが変わる）
- 先に必要な特性テスト: `ProposedMasterCreation` に ai_ci で既存と衝突する別表記（例: 既存「ハ…」に対して「バ…」）を渡すと、いまは既存のレコードが返り、件数が増えないことを固定する。

### [A06-3] RecordNotUnique は決定的には起きないが、タグ統括管理は競合時に 500 になる。新設候補と seed は Rails 8.1 の暗黙の挙動に頼っている
- 観点: E ／ 確度: 確認済み（コードと Rails 8.1.3.1 のソースを読んで確かめた。競合の再現はしていない）
- 根拠:
  - 一意性検証は `default_uniqueness_comparison` = `attribute.eq(value)`（activerecord-8.1.3.1 validations/uniqueness.rb:120-121、abstract_adapter.rb:873-875）なので、列の照合順序 `utf8mb4_0900_ai_ci` で比べる。一意索引も同じ列・同じ照合順序（schema.rb:36,46,54,61,99）。スコープも揃っている（genre.rb:15 の `scope: :parent_id` と `uq_genres_parent_name`）。したがって「検証は通るのに索引で弾かれる」決定的な経路は無い。
  - `Admin::TagsController#create`（tags_controller.rb:22-23）と `#update`（:38）は `save` / `update` のあとの `RecordNotUnique` を rescue していない。
  - P3・P4 の `find_or_create_by!` は、Rails 8.1 では `find_by || create_or_find_by!`（relation.rb:238-240）になり、`RecordNotUnique` を rescue して `find_by!` する（:301-306）。これはコードに表明されていない Rails のバージョン依存で、Rails 7.x の `find_or_create_by!` は rescue しなかった。
  - 大分類（`parent_id` が NULL）は、一意索引が NULL どうしを区別しないので、検証でしか守られていない（genre.rb:13-15 のコメントのとおり）。P1 で大分類を同時に作ると、例外も出ずに重複ができうる。
- 問題: 管理者は 1 人なので、実際に起きる見込みは低い。ただし P1 だけが明示的に rescue していて、P3・P4 は暗黙、P2 は無防備、という差が読み取れない。
- 提案: `TagsController#create` / `#update` に `rescue ActiveRecord::RecordNotUnique` を足して 422 を返す。P3 のコメントに「競合は `find_or_create_by!`（Rails 8.1 以降は create_or_find_by! 経由）が吸収する」と 1 行書く。
- リスク: 低 ／ 外部振る舞いへの影響: なし（競合時の 500 が 422 になるだけ）
- 先に必要な特性テスト: 不要（競合は再現しにくい）。直すなら `save` が `RecordNotUnique` を投げるようにスタブしたコントローラテストを 1 本足す。

### [A06-4] マスタ名の同一判定が「SQL の ai_ci」と「Ruby の完全一致」で混ざっている
- 観点: E・B ／ 確度: 確認済み（コード）。表示上の結果は、ai_ci の同一視の仕様から導いた推測で、実行はしていない
- 根拠:
  - `SenseProposal#resolved_word_origins` は `WordOrigin.where(name:)` を使うので ai_ci で解決する。一方 `#unknown_word_origin_names` は `word_origin_names - resolved_word_origins.pluck(:name)` で、Ruby の完全一致で引き算している（annotation_proposal.rb:82-83）。
    - ai_ci で同じ扱いになる別表記（半角カナ、ひらがなとカタカナ、清濁の違いなど）が payload に入ると、その語種は「解決済み」の欄（_proposal_sense.html.erb:62）と「新設候補」のボタン（:63-66）の**両方に出る**。
    - ボタンを押しても P3 の `find_or_create_by!` は既存を返すだけなので、候補は消えない。
    - `BulkProposalApproval` のゲート（bulk_proposal_approval.rb:24）もこの語を一括承認から外す。
    - 一方で `ProposalApplication`（proposal_application.rb:47）は既存の語種を入れる。
  - `SeedCatalog.seeded?`（seed_catalog.rb:328-332,345-355）は `include?` による完全一致で判定する。これに対し `apply_simple!` / `apply_genres!`（:299,308,313）は ai_ci の `find_or_create_by!` を使う。ai_ci で同じ扱いになる表記にリネームすると、「seed」の印は消えるが、deploy:seed は新しい名前のレコードを既存とみなす。
  - 意図して両方を使い分けているのは、P1 の `existing.name == name`（inline_master_creatable.rb:23）だけ。
- 問題: 同じ「この名前のマスタはあるか」という問いに、2 通りの答えが混在している。M-20 は「提案の解決は ai_ci に依存する」と表明するよう求めているが、そのうえで Ruby 側の完全一致が混ざっていることは書かれていない。
- 提案: `unknown_word_origin_names` を「解決できたレコードのどれにも ai_ci で当たらない名前」に直す。たとえば名前ごとに `WordOrigin.exists?(name:)` で確かめる。`seeded?` には「完全一致で判定する」とコメントを付ける。比較の規則を M-20 の表明と同じ場所に書く。
- リスク: 低 ／ 外部振る舞いへの影響: あり（管理画面の新設候補の表示と、一括承認の対象が変わる）
- 先に必要な特性テスト: annotation_proposal_test.rb:51-59 の隣に、ai_ci で既存と同じ扱いになる別表記の語種名を入れたときの `unknown_word_origin_names` の現状の値を固定する（DB の照合順序を通るテストが要る）。

### [A06-5] 新設候補の案内が逆を向いている（失敗時は「タグ統括管理から」、特徴は「その場追加が要る」と書くが、実装はその逆）
- 観点: A ／ 確度: 確認済み
- 根拠:
  - P3 が失敗したときの文言は「タグ統括管理から手動で追加してください」（ja.yml:1051 `admin.annotations.create_master_failed`。annotations_controller.rb:86、annotation_decks_controller.rb:80）。しかしタグ統括管理で追加できるのは言語的特徴だけで（tag_kind.rb:40-45）、P3 が扱う 4 種は追加できない。
  - 提案パネルのコメント（_proposal_sense.html.erb:74-75）は、未知の特徴名について「その場追加が要る」と書く。しかし特徴のその場追加は無い（routes.rb:137-139 と _sense_fields.html.erb の inline-add は、語種・品詞・エンティティ・ジャンルだけ）。特徴を足せるのは P2 だけ。
- 問題: 管理者も、エージェントも、失敗したあとの行き先を誤る。エージェントがコメントを信じて「特徴のその場追加」を探しても見つからない。
- 提案: ja.yml:1051 を「コンソールのその場追加から」に、_proposal_sense.html.erb:74-75 のコメントを「タグ統括管理で追加」に直す。
- リスク: 低 ／ 外部振る舞いへの影響: あり（管理画面のエラー文言 1 つ。公開面はなし）
- 先に必要な特性テスト: 不要（文言とコメントだけ）。

### [A06-6] ProposedMasterCreation の冒頭コメントは「提案の未知の名前だけ」と読めるが、語種はリクエストの name をそのまま使う
- 観点: A ／ 確度: 確認済み
- 根拠:
  - proposed_master_creation.rb:1-3 は「field で種別を絞り、未知の名前だけをその場でマスタ化する」と書いている。
  - しかし `when "word_origin" then create_named(WordOrigin, @name)`（:24）の `@name` は `params[:name]`（annotations_controller.rb:82、annotation_decks_controller.rb:76）。その名前が `@sense.word_origin_names` に含まれるかどうかは確かめていない。ほかの 3 種は payload から名前を取る。
- 問題: 管理者だけが使う経路なので、セキュリティ上の害は無い。ただ「提案の名前に限って作る」という不変条件がコードに無く、コメントだけがそれを示している。エージェントが「名前は提案から来る」と思い込んで、検証を省いたまま別の経路に流用するおそれがある。
- 提案: `@name` が `@sense.unknown_word_origin_names` に含まれることを確かめて、含まれなければ `Error` にする。または、コメントを「語種は呼び出し側が渡した名前で作る」と事実どおりに直す。
- リスク: 低 ／ 外部振る舞いへの影響: なし（コメントを直す場合）／ あり（検証を足す場合。細工したリクエストが Error になる）
- 先に必要な特性テスト: proposed_master_creation_test.rb:25 の隣に、「提案に無い語種名を渡すと、いまは作られる」ことを固定するテスト。

### [A06-7] マスタ名の長さの上限（varchar 255）を検証している経路が無く、超えると 500 になる
- 観点: E ／ 確度: 推測（本番サーバの `database.yml` と sql_mode は見ていない）
- 根拠:
  - name 列は `t.string`、つまり varchar(255)（schema.rb:34,42,52,59,97）。モデルに `length` の検証は無い。
  - リポジトリの database.yml には `strict` の指定が無いので、Rails の既定（`strict_mode?` は既定で true。abstract_mysql_adapter.rb:656-657）で STRICT_ALL_TABLES になり、長すぎる値は `ActiveRecord::ValueTooLong`（:867-868）になる。
  - P1 は `RecordNotUnique` だけを、P3 は `Error` / `RecordInvalid` だけを rescue している。P2 は何も rescue していない。
- 問題: 256 文字を超える名前を入れると、管理画面が 500 になる。CFG-13 は長さ 768 の列を挙げているが、マスタ名の 255 は挙げていない。
- 提案: 5 つのモデルに `validates :name, length: { maximum: 255 }` を足す。CFG-13 と同じ改修項目に束ねる。
- リスク: 低 ／ 外部振る舞いへの影響: あり（500 が検証エラーになるだけ）
