# A-09: 公開スコープを通らない経路の洗い出し

## 結論（3〜5 行）

- 未ログインで到達できる出力のうち、語の内容（表層形・読み・意味など）を出す経路は、すべて `Word.annotated`（word.rb:20）か `WordSense.published`（word_sense.rb:56）を通ります。通らない経路も、この2つで選んだ id を受け取るだけです。いま公開中かどうかの判定が恒久的に漏れる経路は見つかりませんでした（確認済み）。
- ただし**公開を取り消した語（保留・削除）は、キャッシュの TTL のあいだ公開面に残ります**。`/llms-full.txt`・`/rankings`・`/stats`（特徴の実例）には表層形や読みが、`/sitemap.xml` には URL が、最長でおよそ1日残ります。時間に限りのある漏れです（[A09-1]、確認済み）。
- data-model.md §8 の「すべてがこのスコープを通る」は言い過ぎです。次の3つは、リクエストの時点ではスコープを通りません。いずれも語の漏れではありません（[A09-2]）。
  - 統計のワードクラウド。コミット済みの事前集計ファイルを読みます。
  - マスタの全件表示。
  - ホームの「ジャンル数」。
- `WordBatch` は「渡される id は公開語のもの」という前提に依存していますが、その前提がどこにも書かれていません（[A09-3]）。
- 公開条件の書き方が揺れている件は C-12 と同じです。補足として、3つ目の書き方 `joins(word_sense: :word).merge(Word.annotated)` があります（site_statistics.rb:83,121,225,356,368）。

## 指摘

### [A09-1] 公開を取り消した語（保留・削除）が、キャッシュ済みの公開出力に最長でおよそ1日残る
- 観点: E（暗黙の前提・不具合）／ 確度: 確認済み（コードと呼び出し元を読んで裏付けた。実行はしていない）
- 根拠:
  - 公開済みの語を未公開に戻す経路があります:
    - admin/annotations_controller.rb:58-62 `hold` → word.rb:44-47 `mark_on_hold` が `annotated_at = nil` にして `save!` します。
    - `set_word`（:109-112）は状態を問わず `Word.find` します。保留ボタン（admin/annotations/show.html.erb:111-113）にも条件はありません。
    - word.rb:36-37 のコメントは「保留でいったん未公開に戻した語」を想定しています。
    - 削除は admin/words_controller.rb:93-96 です。
  - 次のキャッシュは、公開を取り消しても無効になりません:
    - **llms-full.txt / sitemap.xml**:
      - 鍵は published_words_digest.rb:33-35 `published_words_version` で、`Word.annotated.maximum(:updated_at)` を日単位に畳んだものです。
      - 保留にした語は集合から抜けます。そのため、その語が保存で更新した updated_at は版に入りません。残った公開語の最大値が同じ日に属する限り、版も鍵も変わりません。
      - その結果、llms_controller.rb:23-24 と sitemaps_controller.rb:20-21 はキャッシュ済みの本文をそのまま返し、`stale?`（llms_controller.rb:21、sitemaps_controller.rb:18）は 304 を返します。
      - 本文の保持は CACHE_TTL = 1.day まで（llms_controller.rb:8、sitemaps_controller.rb:15）です。さらに `expires_in 1.day, public: true` により、ブラウザや中継キャッシュにも最長1日残ります。
    - **/rankings**: word_ranking.rb:59 は固定キー `"word_rankings/v1/<key>/<limit>"` で1日キャッシュします。中身は表層形と読みです（:73-76 `build_top`）。
    - **/stats**: site_statistics.rb:34 は固定キーで1日キャッシュします。特徴の実例（:365-374 `feature_example`）が表層形を持ちます。stats/_feature_ranking.html.erb:14-21 がそれを表示します。
    - 数だけのもの:
      - home_controller.rb:11（1時間）
      - pages_controller.rb:9（1日）
      - published_sense_counts.rb:8, 27（1時間。/genres では、取り消した語にしか使われていない分類も最長1時間表示される）
  - 本番の cache_store は `:memory_store` です（config/environments/production.rb:69）。再起動やデプロイで消えますが、それ以外に消す仕組みはありません（`Rails.cache.delete` は 0 件。M-18）。
  - 前提がコメントに書かれていません:
    - published_words_digest.rb:27-29 は「アノテーションの保存は未公開の語を公開する操作」とだけ書いていて、逆向き（公開の取り消し）を想定していません。
    - :31-32 は削除にだけ触れ、「遅くとも翌日には作り直される」と書いています。
  - 対照として、取り消しがすぐ反映される経路もあります:
    - /words/:id・/words・Atom・共有カードは、キャッシュの前に毎回スコープを引きます（words_controller.rb:37, 126, 106、share_cards_controller.rb:10）。
    - 重複チェックの鍵には件数が入っています（word_request_duplicate_check.rb:55-58）。
- 再現の道筋（llms-full.txt。cache_store がメモリストアの環境、たとえば本番や `dev:cache` を有効にした development）:
  1. 公開語 W があり、W 以外にも当日に updated_at が更新された公開語がある状態で、`GET /llms-full.txt` を取得します。W を含む本文が `llms_full/v2/<当日0時のepoch>` に入ります。
  2. 管理者が `/admin/annotations/W` で「保留」を押します（`PATCH /admin/annotations/W/hold`）。W の annotated_at が NULL になります。
  3. `GET /llms-full.txt` を取得すると、鍵が同じなので、W の表層形・読み・意味を含む本文がそのまま返ります。ETag も同じです。
  - /rankings の場合は、W が上位 TOP_LIMIT+1 件に入っていれば、手順 1→3 と同じ流れで、日をまたいでも1日以内は W が出ます。リンク先は 404 です。
- 問題:
  - data-model.md §8 の「公開されるのは annotated_at が立っている語だけ」が、公開を取り消した直後には成り立ちません。
  - 出続けるのは表層形・読み・意味です。llms-full.txt は CC BY 4.0 で配っているデータでもあります。
  - 頻度は低いものの、オーナーが「出したくない」と判断して保留に戻した語ほど影響が大きくなります。
  - この前提はコードからも文書からも読み取れません。そのため、将来のエージェントがキャッシュを足すと、同じ穴を作ります。
- 提案（外部の振る舞いが変わるので、計画書への提案にとどめる）:
  - (a) 文書化だけにする場合: 次の2か所に「公開の取り消し（保留・削除）は、キャッシュの TTL のあいだ反映されない」と書きます。振る舞いは変わりません。
    - published_words_digest.rb の冒頭
    - data-model.md §8
  - (b) 直す場合: 取り消し（`hold` / `destroy`）の後に、公開集計のキャッシュを明示的に消します。対象は llms_full・sitemap・word_rankings・site_statistics・published_sense_counts・home/stats です。取り消しはまれなので、作り直しのコストは許容できる見込みです（推測）。
  - 版に件数を混ぜる案は、published_words_digest.rb:27-29 が性能上の理由で退けているので採りません。
  - どちらにするかはオーナーが判断します。
- リスク: 中 ／ 外部振る舞いへの影響: (a) ならなし。(b) ならあり（取り消した直後から、その語が上の各出力から消える。ETag も変わる）
- 先に必要な特性テスト:
  - 次のテストを1本の結合テストで書き、いまの挙動（残る）を固定します。
    - キャッシュを有効にする（`Rails.cache` と `ActionController::Base.cache_store` の両方をメモリストアに差し替える）。
    - 公開語を、同じ日に更新された公開語がもう1つある状態で保留にする。
    - その後の `/llms-full.txt`・`/sitemap.xml`・`/rankings`・`/stats` に、その語が出るかを確かめる。
  - (b) を採るなら、このテストの期待を反転させます。
  - 既存の test/integration/published_words_digest_test.rb は公開する方向（:22, :36）だけで、取り消しの方向はありません。

### [A09-2] data-model.md §8 の「すべてがこのスコープを通る」に例外が3種あり、文書に書かれていない
- 観点: A（文書・コメントと実装の矛盾）／ 確度: 確認済み（どれも語の漏れではない。ワードクラウドの生成手順が守られているかは推測）
- 根拠:
  - data-model.md:200-201 は「一覧・検索・sitemap・API・統計のすべてがこのスコープを通る」と書いています。
  - 例外1、ワードクラウド:
    - stats/_word_cloud.html.erb:8 `MorphemeFrequencies.entries` は、コミット済みの db/morpheme_frequencies.json を読むだけです（morpheme_frequencies.rb:10, 68-69）。

    - 手順はコメントの「llms-full.txt から抜く」（stats.rake:11-13）に頼っているだけで、コードでは強制されていません。
    - いまのファイルは generated_at 2026-09-10・word_count 1476 のスナップショットです。生成後に取り消した語の部品も残り続けます。ただし MIN_COUNT = 2（morpheme_frequencies.rb:16）なので、1語にしか現れない部品は載りません。
  - 例外2、マスタの全件表示:
    - /search のフォーム（searches_controller.rb:24-30、searches/_genre_filter.html.erb:16）と、ファセットの見出し（words_helper.rb:81）は、公開語に使われていないマスタの名前も出します。

    - マスタは、未公開語の提案からも作られます（admin/annotations_controller.rb:78-82 `create_master`、ProposedMasterCreation）。そのため、未公開語のためだけに作った分類名が公開面に出ることがあります（推測: 実データは見ていない）。

  - マスタを「使用中だけ見せる」に揃えるかどうかは、表示が変わるので計画書への提案にとどめます。

### [A09-3] `WordBatch` は公開スコープを持たず、「預かる id は公開語のもの」という前提が書かれていない
- 観点: E（暗黙の前提）／ 確度: 確認済み
- 根拠:
  - word_batch.rb:32-34 `loaded` は `Word.where(id: @reserved_ids)` で、`annotated` を掛けていません。
  - クラスの冒頭コメント（:1-5）は「単語詳細の複数の区画が出す語をまとめて読み込む」とだけ書き、公開条件には触れていません。
  - いまの呼び出し元は2つで、どちらも `WordSense.published` 由来の id だけを `reserve` しています。
    - related_words.rb:43-51
    - shiritori_words.rb:22, 47-51
  - 結果は公開ページの一覧行（words/show.html.erb:238, 261）にそのまま描かれます。
- 問題:
  - 「区画を1つ足す」変更で、エージェントが別のスコープから id を預けると、未公開語が詳細ページに出ます。
  - その危険を知らせるものが、クラスにもテストにもありません。
- 提案（振る舞いは変わらない）: 次のどちらかにします。
  - `loaded` を `Word.annotated.where(id: …)` にする。いまの id はすべて公開語なので、結果は同じです。
  - 冒頭コメントに「公開語の id だけを預けること」と書く。
- リスク: 低 ／ 外部振る舞いへの影響: なし
- 先に必要な特性テスト:
  - word_batch_test.rb に、未公開語の id を `reserve` したときに `words_for` が返すものを固定するテストを足します。スコープを掛けるなら、「返さない」をテストにします。
  - related_words_test.rb には、未公開語を除外するテストがありません（shiritori_words_test.rb にはあります）。これも足します。

- 本番 DB の中身（未公開語のためだけに作られたマスタが実在するか、ワードクラウドのファイルを `SURFACES_FILE` で作ったか）は見ていません。
- 管理画面（`/admin`）は認証必須なので、公開スコープの観点では見ていません。

## リーダーの裏取り（6f59f21）

- A09-1 の sitemap・llms-full の経路は実在する（`app/controllers/concerns/published_words_digest.rb` の `published_words_version` は `Word.annotated.maximum(:updated_at)` を日単位に畳んだもので、公開語が減っても変わらない）。
- ただし、これは**意図的な割り切り**である。同じファイルの冒頭コメントが、性能（Puma 1 プロセス・GIL での再生成の詰まり）を理由に「最大 1 日の遅れは元々の契約どおり（`expires_in 1.day, public`）」と書き、`published_words_version` のコメントも「削除だけが起きた場合は最終更新日が動かないが、…遅くとも翌日には作り直される」と書いている。
- 一方で、ランキングと統計の固定キーのキャッシュについては、同じ割り切りがどこに書かれているかを確かめていない。
- したがって、A09-1 の扱いは「不具合として直す」ではなく、**「公開取り消しが最大 1 日遅れることを、オーナーが許容するかの判断」**とする。許容するなら、data-model.md §8 に例外として書く（A09-2 と同じ項目にまとめられる）。許容しないなら §7.1（振る舞いの変更）の扱いになる。台帳 P-04 の質問に入れる。
