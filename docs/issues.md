# 実装 Issue リスト(単語収集・解析アプリ)

段階的な実装計画と改善バックログ。**1 Issue = 1 ブランチ = 1 PR** を原則とする。

- アプリ全体像・実装状況・ローカル環境: [`docs/overview.md`](overview.md)
- データモデル・横断方針(照合順序・公開方針など): [`CLAUDE.md`](../CLAUDE.md) / [`docs/schema.sql`](schema.sql)
- グロース戦略と現状評価: [`docs/growth-strategy.md`](growth-strategy.md)
- 収録基準の正: [`docs/annotation-guidelines.md`](annotation-guidelines.md)

## 記述フォーマット(統一)

各 Issue は次の形式で記述する。完了した Issue は詳細を落として「完了アーカイブ」節へ要約して移す(経緯の詳細は git 履歴で参照できる)。

```
## Issue N: タイトル
- 種別: feature / improvement / bug / ops
- 状態: 未着手 / 対応中 / 保留(理由) / 完了(PR #n)
- 優先度: P0〜P2 ／ Impact: High/Med/Low ／ Effort: High/Med/Low
- 依存: Issue n / なし
- 背景・現状: (1〜3行)
- 内容: (チェックリスト)
- 期待効果: (1〜2行)
```

- 種別 `ops` = コード変更を伴わない(または僅かな)運用・インフラ作業。
- 優先度の目安: P0 = 公開(インデックス解禁)の前提条件、P1 = 解禁前後に済ませたい土台、P2 = データ量・トラフィックの成長に合わせて。

## 公開側からの収録リクエスト(Issue 75、2026-08-02)

- **Issue 75: 収録リクエスト(公開側からの単語リクエスト受付)** [feature] — 完了(PR #118)。2026-07-15 から「要件を詰めてから」として保留していた件(確定事項 #12)の実装。**閲覧専用だった公開面に初めて開けた書き込み経路**で、要件は確定事項 #19・#20 のとおり。

## クロール予算の是正(Issue 80、2026-08-20)

- **Issue 80: シャッフルの無限クロールトラップと、面の棚卸し** [bug] — 完了(2026-08-20)。2026-08-20 の Search Console レポート(**noindex 除外 3,186** ・robots.txt ブロック 102・検出未登録 96・クロール済み未登録 13)と、7月末から約半減した表示回数(約250/日 → 約110/日)の原因調査。**Issue 74 の対応(2026-07-28 時点で noindex 309)から3週間で 10 倍に増えていた**。
  - **原因はシャッフルのリンク**。`shuffle_words_path` が `SecureRandom.hex(4)` を href に埋めていたため、**一覧を描画するたびに未知の URL が生まれる**。しかもこのボタンは素の一覧・全ファセット面・全ページ送りに置かれ、`rel="nofollow"` も robots.txt のブロックも無く、**辿った先でもまた新しい URL が生まれる**。事実上の無限 URL 空間で、クローラが延々と noindex ページを取りに来ていた。導入は 2026-07-21(`58cbe66`)で、GSC の未登録数が 7/24 の 449 → 7/25 に 1,910 へ急増し以降**単調増加**(2,620 → 2,919 → 2,961 → 3,423)している推移と一致する。本物のページのクロールが後回しになり(「検出 - インデックス未登録」96)、表示回数の低下につながっていた。
  - **対応(1) 生成元を絶つ**: シードを **href から外してサーバ側(`WordSort`)で振る**。URL に無ければリクエストごとに新しいシードを引くので「押すたび・開くたびに引き直す」挙動はそのまま、**絞り込み1つにつきシャッフルの URL はちょうど1本**に収まる。ページ送りは実際に使ったシードを引き継ぐが、そのリンクには `rel="nofollow"` を付ける。ボタン自体にも `nofollow`(結果は必ず並び違いの重複 = noindex なのでクロールの価値が無い)。
  - **対応(2) 既知の分も止める**: robots.txt に `Disallow: /*seed=`。`/search` と違い**元から実在しないページ**なので noindex を読ませる必要がなく、再クロールごと遮断してよい(Issue 74 で `/search` をブロックしなかった判断とは前提が異なる)。
  - **対応(3) 面の棚卸し**: 統計・索引から常時リンクしているのに noindex のままクロールだけさせていた軸を **インデックス許可に格上げ**(`reading_length` / `mora_count` / `linguistic_feature_id`、実測で計約 56 URL)。いずれも値域が有限で、「読みが15文字の長い言葉」「回文の長い言葉」のように**本サイトの検索需要そのもの**になる面。見出しは `words.index.facet_heading.reading_length` / `.mora_count` を追加。
  - **対応(4) 残る noindex 行きに `nofollow`**: ワードクラウドの形態素チップ(キーワード検索 `q=`。実測 60 URL → 2026-09-10 に 100 URL)、頭子音の**複数文字**をまとめて渡す棒(1文字だけの群はスカラ形 = 単一ファセットなので**辿らせたまま**)、波形バーの「◯以上」(範囲指定 `reading_length_min`)、`/words/random`(毎回別の語へ 302 する導線)。
  - **効果の見込み**: 内部リンクから辿れる noindex URL が有限(素の一覧 + 各面 1 本)になり、クロール予算が単語詳細と単一ファセットへ回る。既存の 3,186 件は robots.txt で再クロールが止まり、GSC 上は「robots.txt によりブロックされました」へ移ってから漸減する。**(この最後の見込みは Issue 81 で撤回。ブロックすると canonical の訂正を読ませられないため `Disallow: /*seed=` は外した)**

## ファセット面の是正(Issue 81、2026-08-25)

- **Issue 81: ファセットの canonical 破れと、実在しない面** [bug] — 完了(2026-08-25)。Issue 80 の対応後も残っていた、面まわりの取りこぼし5点。
  - **canonical の二重エスケープ**: `content_for(:canonical_path)` は値を HTML エスケープして貯めるため、クエリの `&` が `&amp;` になり、レイアウトの `<%= %>` でもう一度エスケープされて `?a=1&amp;amp;b=2` になっていた。クローラから見ると「amp;b」という実在しないパラメータ名の URL を canonical に指名している状態。`canonical_path(...)` ヘルパー(インスタンス変数)に替えて経路からエスケープを外した。
  - **noindex の伝播**: `/words?sort=…` は必ず noindex だが、canonical には sort を含めず `/words` を指していた。**noindex のページが他の URL を canonical に指名すると、その指し先へ noindex が伝播しうる**(Google 公式ガイダンス)ため、サイトのハブである `/words` を巻き添えにする恐れがあった。canonical に sort を含め、自身を指させて断つ。シャッフルの seed は URL に載せない値なので canonical も seed 抜きの1本に寄せる。
  - **実在しないマスタ id で面が無限に湧く**: `genre_id=99999` のような値は絞り込みごと落ちるため **`/words` の完全な複製**が任意の数値ぶん作れ(しかも index 可能・自己 canonical)、他の軸は 0 件の面が同じく無限に作れた。`WordSenseSearch#unknown_master_ids?` を追加し、コントローラで 404 にして URL 空間を閉じる。判定に使う対応表(`MASTER_FACETS`)は見出しの解決(`WordsHelper::FACET_MASTERS`)と共有し、片方だけ軸が増えるのを防ぐ。
  - **0 件のファセット面を noindex**: 実在する軸でも公開語が 0 のもの(連声・音韻添加など。Issue 77)や `reading_length=99` のように値だけ無いものがあり、中身の無い面をクロールさせても「クロール済み - インデックス未登録」が増えるだけのため。
  - **`Disallow: /*seed=` を撤去**: Issue 80 の対応(2)を**取り消した**。既知の 3,186 件は当時「noindex + canonical は `/words`」を宣言済みで、ブロックすると Google がその訂正(canonical を自身へ向けた上記の修正)を読めず、宣言が凍結されて `/words` へ noindex が伝播したままになる。生成元は既に絶ってあるので新しい `?seed=` は増えず、既知の分は再クロールで noindex に落ちる。あわせてランキングの「すべて見る」(必ず noindex の並び違いへ行く導線)に `rel="nofollow"`。

## 2026-08-02(収録リクエスト機能の要件確定)

19. **リクエスト機能の要件を確定**(2026-07-15 の保留 #12 の決着。Issue 75 として起票)。
    - **受け付けるのは収録リクエストのみ**。訂正報告・機能要望・汎用お問い合わせは対象外(従来どおり About のメール)。
    - **投稿は非公開の投稿箱**。公開一覧は作らない(荒らしを公開面に出さず、モデレーション義務を負わない)。反応を見てから広げる。
    - **連絡先欄は設けない**(メールもニックネームも受け取らない) → 返信はせず、メール基盤(SMTP)も導入しない。ただし送信メタデータは保存する(#20 で確定)ため「完全匿名」とは称さない。
    - **スパム対策はアプリ側の軽量策のみ**(ハニーポット+経過秒数+レートリミット+文字数上限)。Turnstile 等の外部 JS は入れない(CDN 不使用・JS 最小・自己完結の方針を曲げない)。
    - **入口は2つ**: 検索結果0件の区画(キーワードをプリフィル)とフッター・About。**フォーム本体は専用ページに置く**(公開一覧は `public: true` の HTTP キャッシュ配下のため、CSRF トークン入りフォームを埋め込まない)。
    - **読みは任意**で、入れた場合だけ字数カウンタで収録基準(10文字以上)を示す。基準未満でも送信は弾かない。
    - **管理側は一覧+ステータス+一括登録 step1 への流し込み**まで作る(収録までの動線を切らさない)。気づき方は未着手件数バッジのみ、逃げ道として `REQUESTS_ENABLED` で受付停止。

20. **リクエスト機能に重複チェック・メタデータ保存・送信上限を追加**(同日の追加指示。#19 の一部を上書き)。
    - **重複チェックは「重複チェックする」ボタンによる任意操作**にする。**送信時には発火させず、重複があっても送信は妨げない**。押下でローディングを挟み、結果をメッセージで返す。ロジックは管理画面と同じ `Levenshtein`(閾値 0.8)を流用し、**読みがあれば読み、無ければ表層形**に当てる。該当なしの「**登録が確認されませんでした**」というメッセージ自体が、利用者に発見と参画の手応えを与える狙い(オーナー発案)。
    - **取得できるメタデータは原則すべてレコードに保存する**(IP アドレス・User-Agent・リファラー・送信元パス)。今後の解析とアプリケーション発展の材料にするため。→ **#19 の「IP を DB に残さない」は撤回**し、**プライバシーポリシーの改訂を必須**とする(保存する情報と利用目的を明記)。
    - **レートリミットは保存したメタデータと `created_at` の COUNT で判定**する(送信については自前カウンタを用意しない)。ただし**重複チェックはレコードを作らない**ため、そちらだけは別途キャッシュで軽く制限する。
    - **1通あたりの送信上限は10語**。フォームは行追加式(各行に 単語/読み/ひとこと)。上限はサーバ側でも検証する。
    - 重複チェックは既存語の総なめ(Issue 52 で指摘済みの負荷)を**公開側に露出させる**ため、既存 (reading, surface) 一覧を `Rails.cache` に載せてから公開する。
    - **管理画面のステータスは 未着手 / 採用済み / 保留 / 却下** の4種。**遷移のタイミング(手動か自動か)は単語登録までの動線を確認してから再度詰める(TBD)**。
