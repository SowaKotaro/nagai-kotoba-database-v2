# 1語の再アノテーション調査（オフライン）

すでに注釈が付いている（または提案が取り込まれている）語について、**オーナーが「この注釈は微妙だ」と
思った項目だけ**を調べ直すためのタスク。スマートフォンからでも回せるよう、**入力は会話に貼られた JSON、
出力はチャットに貼り付け用の JSON** で完結させる。

まとめての下調べは `word-annotation-research`（`/annotation`）。**取り違えないこと。**

## 全体の流れ

1. 入力 JSON を読み取る（会話に貼られたもの／ファイル）。
2. **どの項目を調べ直すか AskUserQuestion で確認する**（勝手に全項目やり直さない）。
3. 選ばれた項目だけを調べ直す（判断基準・手順は `word-annotation-research` に従う）。
4. **選ばれなかった項目は現在値をそのまま素通し**して、語の全項目が揃った提案 JSON をチャットに出す。

## 判断基準は既存スキルが正

**調査を始める前に必ず [`.claude/skills/word-annotation-research/SKILL.md`](../word-annotation-research/SKILL.md)
を Read する。** 意味の文体・ジャンルとエンティティの切り分け・語種の付け方・言語的特徴の「分解と突き合わせ」・
別表記の類型・立項スコアの定義は、すべてあちらが正。ここではその手順番号（手順3=意味、手順4=ジャンル、
手順5=エンティティ、手順6=品詞、手順7=語種、手順8=言語的特徴、手順9=別表記）を参照するだけにする。
収録基準の正が [`docs/annotation-guidelines.md`](../../../docs/annotation-guidelines.md) であることも同じ。

**「2周で調べる」も同じく適用する。** 1語だけなので、まとめての調査より丁寧にできるはず。むしろ
ここに来た語は「1周目の結果が怪しい」と人が判断した語なので、**裏取りの手を抜かない**。

## 入力

次のいずれか。上から順に探す。

1. **コマンド引数として会話に貼られた JSON**（通常はこれ。`/reannotation` の後ろに貼られる）
2. 引数がファイルパスなら、そのファイル
3. どちらも無ければ `research/inputs/reannotation.json`
4. それも無ければ**その場で聞く**（勝手に DB や公開 API から語を探しに行かない）

JSON は管理画面のアノテーション・コンソール（`/admin/annotations/:id`）の「再調査用JSON →」から
コピーしたもので、形は次のとおり:

```json
{
  "version": "1",
  "format": "reannotation",
  "word_id": 123,
  "surface": "活版印刷術",
  "reading": "かっぱんいんさつじゅつ",
  "current": {
    "source": "saved",
    "senses": [ { "meaning": "…", "genre_path": ["…","…","…"], "entity_type": "…", "part_of_speech": "…", "word_origins": ["…"], "linguistic_features": [], "variants": [] } ],
    "entry_score": 5,
    "confidence": "high",
    "notes": "…"
  },
  "masters": { "genres": { "大分類": { "中分類": ["小分類", …] } }, "entity_types": [], "parts_of_speech": [], "word_origins": [], "linguistic_features": [] }
}
```

- `current.source` は現在値の出どころ。`saved`=人が保存済みの内容 / `proposal`=取り込んだ提案（未保存） /
  `none`=まだ何も無い。
- **`masters` が入力に無いとき**は、マスタ名を一字一句合わせられない。その場合は勝手に既存名を推測せず、
  「マスタ一覧が無いので名前が既存と一致しない可能性がある」と出力の `notes` に明記する
  （コンソールから「再調査用JSON」を取り直してもらうのが本筋）。
- まとめての書き出し形式（`words` 配列 + `masters`）が貼られたときも受け付ける。その場合は語ごとに
  同じ手順を回し、提案を `proposals` 配列に並べて返す。

## 現在値の扱い（重要）

`current` は**答え合わせの相手**であって、出発点ではない。

- **先に自力で調べてから突き合わせる。** 現在値を読んでから検索を始めると、間違いをなぞって
  「現状どおりで問題なし」と結論しがちになる（アンカリング）。調べ直す項目については、
  まず現在値を見ずに手順どおり調査し、**結論を出してから** `current` と比べる。
- 食い違ったら、**どちらが正しいかを情報源で決める**。現在値が正しければ変更せず、その旨を `notes` に
  1行書く（「意味は現行のままが妥当。〜で確認」）。
- **調べ直さない項目は、値を1文字も変えずにそのまま出力へ写す。** 「ついでに整えた」は禁止。
  オーナーが承認済みの内容を、選んでいない項目で書き換えられるのが一番困る。

## 項目の選択（必ず聞く）

入力を読んだら、**現在の内容を短く要約して見せてから**、AskUserQuestion で調べ直す項目を確認する。
要約は語義ごとに3〜6行（意味／ジャンル／エンティティ／品詞・語種／特徴／別表記）に留める。

質問は **2問の複数選択（multiSelect: true）を1回の AskUserQuestion で**出す:

- 質問1「意味・分類のうち、調べ直すもの」: `意味（説明文）` / `ジャンル` / `エンティティ` / `立項スコア`
- 質問2「表記・その他のうち、調べ直すもの」: `言語的特徴` / `別表記` / `品詞` / `語種`

どちらも選ばれなかった場合は「全項目を調べ直す」と解釈せず、**何をしたいのか聞き直す**。
オーナーが「全部」と答えたときだけ全項目を調べ直す。

**語義が複数ある語**（同音異義語）は、上の質問に加えて「どの語義を調べ直すか」も確認する
（質問は最大4問なので、語義が5つ以上あるときは番号で聞く）。語義の追加・削除が要りそうだと
気づいた場合（同名の別語義を見つけた等）は、勝手に増減させず `notes` で提案する。

## 出力

**チャットに、そのまま「提案 JSON の取り込み」へ貼れる JSON を1つだけ**出す。携帯からコピーするので、
次の順で、**JSON のコードブロックは1つだけ**にする（複数あるとどれをコピーするか迷う）。

1. 変更点の要約（**3〜6行の箇条書き**。「意味: 〜を〜に。理由=〜」の形で、変えなかった項目は
   「据え置き」と1行でまとめる）
2. JSON のコードブロック（```json）

さらに、**ファイルにも書ける環境なら** `research/outputs/reannotation.json` に同じ内容を書き出す
（PC で作業しているときに使う。失敗しても出力自体は成立するので、書けなければ黙って諦める）。

形式は `word-annotation-research` と同じ **`proposals` 配列（要素1つ）+ `senses` 配列**:

```json
{
  "version": "1",
  "proposals": [
    {
      "word_id": 123,
      "surface": "活版印刷術",
      "entry_score": 5,
      "senses": [
        {
          "meaning": "活字を組んで版を作り印刷する技術。グーテンベルクの発明により西洋で普及した。",
          "genre_path": ["歴史・地理", "科学史・技術史", "印刷技術史"],
          "genre_new": false,
          "entity_type": "技術名",
          "part_of_speech": "普通名詞",
          "word_origins": ["日本語"],
          "linguistic_features": [
            { "name": "促音化", "target": "活版", "target_reading": "カッパン" }
          ]
        }
      ],
      "confidence": "high",
      "notes": "再調査(意味・言語的特徴)。意味は現行のままが妥当。特徴は半濁音化を追加した。"
    }
  ]
}
```

出力前に必ず確認する:

- **取り込みは payload を丸ごと上書きする。** 調べ直した項目だけを書いた「部分的な JSON」を返すと、
  据え置いたはずの項目が消える。**`genre_path`・`entity_type`・`part_of_speech`・`word_origins` は
  全語義に必ず入っている**こと（`word-annotation-research` の手順11と同じセルフチェック）。
- `word_id` は入力の値をそのまま返す（突き合わせキー）。
- `linguistic_features` の `target` は表層形の連続部分文字列、`target_reading` はその語義の読みの
  連続部分文字列（取り込み側で検証され、外れると保存できない）。
- `notes` の冒頭に **「再調査(調べ直した項目)。」** と書く。あとでコンソールを見たときに、
  どこを見直した提案なのかが分かる。
- 現在値から**何も変わらなかった**ときも JSON は出す（取り込めば `pending` に戻るので、コンソールで
  改めて確認できる）。ただし要約の1行目で「変更なし」と明言する。
