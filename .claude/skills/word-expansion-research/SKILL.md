# 単語の補完・補足（候補の一括収集・オフライン）

nagai-kotoba-database-v2 に**まだ登録されていない単語の候補を増やす**ための、アプリから切り離した調査タスク。
種語を1つ受け取り、その**上位概念**を突き止め、**種語自身を含めて同じ系統の語をまとめて刈り取る**。
`research/` 配下の入力ファイルを読み、調査結果を出力ファイルに書き出す（**ファイル入力 → 調査 → ファイル出力**）。

これは候補収集の段（[`research/README.md`](../../../research/README.md) の「使う順番」の手順 1）。
出力の JSON は管理画面の拡張の画面に貼り、そこから先は管理画面の流れ（仕分け → 表記 → 登録待ち）に沿う。

## フロー
1. **入力**: `research/inputs/expansion.txt` を読む。1行＝1語（種語）。
   行頭の番号/記号（`1.` `-` `・`）は無視。空行は無視。表層形はスペースを含みうる（例「Dead by Daylight」）＝**行全体を1語**として扱う。
   **行頭が `#<数字>`（例 `#123 泥門デビルバッツ`）のときは、その数字を種語の ID として控え、残りを種語とする**
   （管理画面「登録予定単語」の書き出し形式。ID は JSON 出力でそのまま返す）。
2. **調査**: 種語ごとに 上位概念 → 収集軸の選定 → 同系統の語 の順に WebSearch で調べ、
   全候補の読みの文字数を補助スクリプトで数えて10文字未満を落とす（下記）。
3. **出力**: `research/outputs/expansion.txt`（人が読む版）と `research/outputs/expansion.json`（管理画面に取り込む版）の
   **2つ**を書き出す（どちらも**上書き**）。

## 調べること / 調べないこと
- **調べる**: 種語と**同じ系統の未登録語（候補）を列挙すること**と、各候補の**読みが10文字以上あるか**。
- **調べない**: 表記の正規化（→ `word-notation-research`）、登録する読みの確定（→ `word-reading-research`）、
  意味・ジャンル・品詞・語種（→ `word-annotation-research`）。**候補の表層形を挙げるところまでが仕事**。
  ここで決める読みは**収録基準で候補をふるうためだけ**に使う。JSON には載せず、登録用の読みは後工程の `/reading` が決める。

## 大原則
- **判断基準は [`docs/annotation-guidelines.md`](../../../docs/annotation-guidelines.md) が正。**
  収録の4原則（§1: 公然性・妥当性・慣用性・同定可能性）を満たさない語は**候補に入れない**。
  知られているかどうかの判定は §5（知名度・一般性の判定目安）に従う。
- **でっち上げない（最重要）。** このスキルは「知らない語を大量に出す」ため、**幻覚が最も出やすい**。
  公式サイト・Wikipedia の一覧記事など**実在する一覧を情報源として確認**し、
  そこに載っている語だけを挙げる。一覧が見つからない／断片的にしか確認できない場合は、
  **数を埋めようとせず、確認できた分だけを出して `notes` に「網羅できていない」と書く**。
  「たぶんこういう名前の技もあったはず」で書かない。
- **記憶で書かず、必ず WebSearch する。** 種語がどれだけ有名でも、収集の根拠は毎回引き直す。

## 手順

### 1. 上位概念を特定し、収集軸を選定する
種語を WebSearch し、まず**上位概念**を確定する。

- **上位概念**: その語が属する作品・アーティスト・シリーズ・組織・ブランド・体系など。
  （例: `泥門デビルバッツ` → 漫画『アイシールド21』）

次に、その上位概念から取れる**収集軸**（エンティティの軸）を洗い出し、
**最も有望な軸を1つ選ぶ**。（例: アイシールド21 なら チーム名／キャラクター名／必殺技名）
種語自身の軸（泥門デビルバッツならチーム名）は有力候補だが、自動的には選ばない。
軸の有望さは次で判断する。

- **長い語が見込めるか**: 読み10文字以上になる語が多い軸を優先する。
  短い語ばかりの軸は、一覧がどれだけ充実していても選ばない。
  手順3で10文字未満は**必ず落ちる**ので、「9文字前後の語が大半」の軸（例: `〇〇効果`、`〇〇駐車場`）は、
  残るのが一握りになると見込んで選ぶ。
- **実在する一覧で裏が取れるか**: 公式サイト・Wikipedia の一覧記事など、
  出典にできる一覧が実在する軸を優先する。
- **収録4原則（guidelines §1）を満たす語が見込めるか**。

**1つの種語につき選ぶ軸は1つ**。軸を混ぜると出力のジャンル・エンティティがバラバラになり、
後工程が破綻する。選ばなかった有望軸は収集せず、`notes` に「この軸も取れる」と提案するに留める
（オーナーが次回 `/expand` の引数で指定できる）。

**コマンド引数で軸が指定された場合は、選定を行わずその軸で収集する**（例: `/expand キャラクター名` なら、
有望さの判断を待たずキャラクター名を集める）。

**有望な軸が無い種語は、無理に拡張しない。** どの軸も短い語ばかり／一覧の裏が取れない／
4原則を満たす語が見込めない、という種語は**同系統語0件（種語のみ出力）でよい**。
理由を `--- 注記 ---` に書いて次の種語へ進む。数を出すことより、出した語が全部使えることのほうが大事。

### 2. 同系統の語を列挙する
上位概念 × 収集軸 の一覧を情報源から取る。公式サイトの登場人物/ディスコグラフィ一覧、
Wikipedia の作品記事・一覧記事などを当たり、**出典URLを控える**（出力の `--- 系統 ---` に書く）。

- **上限は 1種語 × 1軸あたり 30語**（種語自身を除き、**手順3の読み10文字以上を通った語だけ**を数える）。
  超える場合は**より一般に知られているもの**から30語を選び、
  `notes` に「他に○件あり」と件数を明記する（オーナーが必要なら次回続きを取る）。
  短い語で枠を使わないよう、30語を選ぶ前に手順3で文字数をふるう。
- **種語自身も出力に含める**。種語が登録済みかどうかはこのスキルでは分からないため、
  同系統の語と同じ扱いで候補リストに並べる。種語はすでに管理画面の候補に入っているので、
  **読みが10文字未満でも先頭に置き**、その旨を `--- 注記 ---` に書く（仕分けの画面で不要にできる）。
- **既に DB に登録済みかどうかは調べない**（このスキルは DB を見ない）。重複は、拡張の画面に取り込むときに
  管理画面が弾く（すでに入っている語・収録済みの語。「この後の流れ」を参照）ので、気にせず候補として出してよい。

### 3. 候補をふるいにかける
次のいずれかに当たる語は、上部の候補リストに入れず `--- 除外した語 ---` に理由付きで落とす。
**捨てずに残す**のは、オーナーが判断を覆して復活させられるようにするため。

- **読みが10文字未満の語（厳密に判定する）**。下の「読みの文字数の判定」の手順で**全候補の読みを決めて数え**、
  10文字未満は1文字足りないだけでも落とす。「だいたい10文字くらい」「際どいので後工程に任せる」で残さない。
- **収録4原則（guidelines §1）を欠く語**。作中に1度しか出てこない語、公式に名前が確認できない通称、
  独立した情報源で裏が取れない語など。

#### 読みの文字数の判定
収録基準は**読み（カタカナ）の文字数が10文字以上**（`WordSense::MIN_READING_LENGTH`）。
**モーラ数でも表層形の字数でもない**。アプリの `word_senses.reading_length`（`char_length(reading)`）と同じ数え方をする。

1. **全候補の読みを決める**。読みの表記ルールは guidelines §4（`word-reading-research` と同じ）に従う。
   - カタカナで書く。長音「ー」・促音「ッ」・拗音「ャュョ」・小書き「ァィゥェォ」は**それぞれ1文字**に数える。
   - 記号・空白・中黒（`・` `=` `!` `〜` `、` など）は読みに含めない＝**数えない**。
   - 英字・数字は読みをカタカナにして数える（`7` → セブン、`M-1` → エムワン）。
   - 助詞は表記どおりのかな（は→ハ、を→ヲ）。
   - 例: `業務上横領罪` = ギョウムジョウオウリョウザイ（14）／`ムペンバ効果` = ムペンバコウカ（7）／
     `梅田ブルク7` = ウメダブルクセブン（9）／`ファイナンシャル・プランナー` = ファイナンシャルプランナー（13）。
2. **暗算で数えず、補助スクリプトで数える**。「表層形<TAB>読み」を1行1語で書いたファイルを渡す:
   ```bash
   bin/rails runner .claude/skills/word-expansion-research/reading_length.rb < <TSVファイル>
   ```
   読みの正規化と数え方はアプリと同じものを使う。MeCab があれば、その読みと文字数も並べて出す。
   出力の判定列:
   - `OK`（10文字以上）→ 候補に残す。
   - `短い`（10文字未満）→ 除外。
   - `要確認`（自分の読みと MeCab の読みで、10文字以上か未満かが分かれた）→ 次の3へ。
   - `読みなし` → 読みを書き忘れている。1に戻る。
3. **読みが割れる語は裏を取る**。`要確認` の語や、読みが複数ありうる語
   （音読み／訓読み、連濁、英字の読み方、`日本`＝ニホン/ニッポン など）は、WebSearch で最も一般的な読みを確かめる。
   - どの読みでも10文字以上 → 残す。どの読みでも10文字未満 → 除外。
   - 一般的な読みでは10文字以上か未満かが分かれ、どちらとも決めきれない → **除外する**
     （理由に「読みが割れ、10文字に届くか未確定」と、それぞれの読みと文字数を書く）。**迷ったら落とす。**
   - MeCab は固有名詞を誤読しやすい（例: `帝黒` をミカドクロと読む）。MeCab の読みは誤りに気づくための参考にとどめ、
     MeCab の読みで判定を決めない。
4. **スクリプトを動かせない環境**（Rails や bundle が使えない等）では、1の規則で1文字ずつ数え、
   各語の読みと文字数を `--- 読みと文字数 ---` に必ず書き出す（書き出す手間で数え違いに気づけるようにする）。

## 出力フォーマット（`research/outputs/expansion.txt`）

先頭に、収集した候補語を**通し番号付きで1行1語**並べる。**種語自身も含める**（種語を先頭に置く）。
**この上部リストはオーナーが目で確かめるための一覧なので、表層形そのものだけを書く**（管理画面への取り込みは
`expansion.json` で行う）。（`（アイシールド21）` などの注記や補足を行末に付けない）。
表記の正規化は次工程の仕事なので、ここでは**情報源に載っている表記のまま**でよい。

続けて次の4節を置く。

- `--- 系統 ---`: 種語ごとに 上位概念 / 収集軸（**選定理由も一言**）/ 出典URL / 収集件数。
- `--- 読みと文字数 ---`: 上部リストの**全語**（種語を含む）を `<語>	<読み>（<文字数>）` で1行ずつ。
  オーナーが文字数の判定を目で確かめられるようにする。
- `--- 除外した語 ---`: `<語>（除外理由）`。**読みが短くて落とした語は、読みと文字数を理由に書く**
  （例: `神龍寺ナーガ（読み シンリュウジナーガ 9文字）`）。無ければこの節は省く。
- `--- 注記 ---`: 種語ごとに confidence（high / medium / low）、網羅できたかどうか、
  上限で切った件数、**他に取れる軸の提案**。**拡張を見送った種語**もここに理由を書く。
  **種語自身の読みが10文字未満**なら、それもここに書く。

例:

```
# 単語の補完・補足（research/inputs/expansion.txt の調査結果）
1. 泥門デビルバッツ
2. 白秋ダイナソアーズ
3. 帝黒アレキサンダーズ
4. 初恋クレイジー

--- 系統 ---
泥門デビルバッツ
  上位概念: 漫画『アイシールド21』（稲垣理一郎・村田雄介）
  収集軸: チーム名（「地名＋ニックネーム」構成で長い語が多く、Wikipedia に一覧があるため選定）
  出典: https://ja.wikipedia.org/wiki/アイシールド21
  収集: 2件 + 種語1件（除外5件）

--- 読みと文字数 ---
泥門デビルバッツ	デイモンデビルバッツ（10）
白秋ダイナソアーズ	ハクシュウダイナソアーズ（12）
帝黒アレキサンダーズ	テイコクアレキサンダーズ（12）
初恋クレイジー	ハツコイクレイジー（9）

--- 除外した語 ---
神龍寺ナーガ（読み シンリュウジナーガ 9文字）
盤戸スパイダーズ（読み バンドスパイダーズ 9文字）
巨深ポセイドン（読み キョシンポセイドン 9文字）
王城ホワイトナイツ（読みは オウジョウホワイトナイツ 12文字だが、公式一覧で表記が割れるため要確認）
NASA エイリアンズ（欧文表記が混在。表記確定が必要）

--- 注記 ---
泥門デビルバッツ: confidence: high。Wikipedia の登場チーム一覧から取得。主要チームは網羅できている。
  読み10文字以上に残ったのは2件だけ（9文字のチーム名が多い）。上限（30語）には達していない。
  他に取れる軸: キャラクター名（例: 小早川瀬那ら）、必殺技名（例: デビルバットゴースト）。
  必要なら `/expand キャラクター名` で再実行できる。
初恋クレイジー: 同系統語0件（拡張見送り。種語のみ出力）。上位概念はスピッツのアルバム『インディゴ地平線』。
  収録曲名の軸は短い曲名が大半で、読み10文字以上が見込める語がほぼ無い。
  アルバム名の軸も同様に短い。有望な軸が無いため無理に拡張しない。
  種語自身も読み ハツコイクレイジー 9文字で収録基準に届かない（仕分けで不要にしてよい）。
```

## 取り込み用 JSON（`research/outputs/expansion.json`）

管理画面「登録予定単語」の拡張の画面に貼るための JSON。**説明文は入れず JSON だけ**を書く。
txt と同じ内容を、種語ごとに束ねて書く。

```json
{
  "version": "1",
  "seeds": [
    {
      "id": 123,
      "input": "泥門デビルバッツ",
      "words": ["泥門デビルバッツ", "白秋ダイナソアーズ", "帝黒アレキサンダーズ"],
      "note": "上位概念: 漫画『アイシールド21』/ 軸: チーム名 / confidence: high"
    },
    { "id": 124, "input": "初恋クレイジー", "words": [], "note": "拡張見送り: 有望な軸なし" }
  ]
}
```

- `id`: 入力行頭の `#<数字>`。**入力にあった ID は必ずすべて返す**（拡張を見送った種語も `words: []` で返す。
  返さなかった種語は管理画面の「拡張待ち」に残ったままになる）。入力に ID が無い行は `id` を省く（取り込めない）。
- `input`: 入力の種語そのまま。
- `words`: txt 上部リストのうちその種語から集めた語（**種語自身を含めてよい**。取り込み側で除く）。
  **除外した語は入れない**（`--- 除外した語 ---` は txt にだけ書く）。**読みも入れない**
  （取り込み側は表層形の配列だけを読む。読みと文字数は txt の `--- 読みと文字数 ---` にだけ書く）。
- `note`: 系統・注記を1〜2文で（上位概念・収集軸・confidence・他に取れる軸）。管理画面のメモに入る。

## この後の流れ
`research/outputs/expansion.json` を管理画面「登録予定単語」の拡張の画面（`/admin/candidates/expand`）に貼る。
種語と集めた語が、仕分けの画面に系統ごとに並ぶ（すでに入っている語・収録済みの語は取り込み側が弾く）。
以降の 仕分け → 表記（`/notation`）→ 登録待ち は管理画面の流れに沿って進める。
